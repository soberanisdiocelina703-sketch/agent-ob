01 看懂问题 · 业务理解

03

入职后的第一个挑战，不是马上开始做，
而是先回答：这件事为什么值得做？

早期探索阶段

先验证功能是否可行

Agent 能否完成任务、流程能否跑通、业务场景是否成立。

逐步投入使用后

开始关注实际运行情况

异常能否及时发现、问题发生在哪一步、排查时是否有足够上下文。

我的理解

KC 等 Agent 业务开始从“把 Agent 建起来”，进入“如何运行和治理 Agent”的阶段。

这也是项目立项的直接背景：业务开始面对上线后的运行、定位和排查问题
我刚接触时只知道 Agent 链路追踪这几个字。结合导师建议和部门正在迭代的 KC 等 Agent 业务，我先理解为什么现在需要它：业务关注点正在从功能能否做出来，转向上线后运行得怎么样。这是我对立项背景的第一层理解。

01 看懂问题 · 概念拆解

04

我逐渐意识到：Agent 链路追踪
不只是“把调用过程画出来”

传统调用链 主要回答“哪里慢、哪里报错”

路径相对固定，技术异常通常会留下报错、超时或状态码。

→
Agent 执行链 还要回答“为什么结果错了”

路径会分支、循环和重试；每一步都可能成功，最终业务结果仍可能不对。

因此需要保留：一次任务中的输入、上下文、推理、工具调用与结果，让排查者能回到原始步骤核对问题如何形成。

传统链路更关注技术故障；Agent 链路还要解释业务语义上的“静默失败”
这页只讲一个区别：传统系统报错往往能从技术信号里找到，Agent 的难点是步骤都成功，结果仍可能错。于是链路的价值不只是展示，而是保留足够的任务上下文，帮助人解释错误怎样形成。

02 找到机会 · 分析判断

05

别人已经做了很多，
我还能从哪里切入？

AgentLoop

生产观测、评估、数据集与审计闭环较完整。

优势：云上生产能力完整

AgentArts

从 Agent 开发、运行到观测的一体化能力较强。

优势：全栈与平台协同

Langfuse

开源、自托管和开发者接入生态更成熟。

优势：开放性与跨框架接入
研究后的机会判断

三家都能展示丰富 Trace 数据；但从公开能力看，把“首个异常—证据—反证—人工复核”组织成统一排障流程，仍有继续验证的空间。

竞品研究的结果不是列功能，而是找到一个尚未被充分解决的问题
第一周我比较了三家产品，并重点拆解 AgentLoop。我看到它们在采集、展示、评估和平台能力上都已经做得很多。因此我没有把机会理解成“再多做一个视图”，而是关注排障者面对大量 Span 时，仍缺少一条可核对的诊断路径。这里要强调“公开能力中未看到成熟答案”，不下绝对结论。

03 做出选择 · 产品思考

06

我的产品判断：不再增加一棵 Trace 树，
先验证“证据化诊断”能否降低排障成本

竞品已经解决较多

把执行过程展示出来

  • 调用树、时序线、链路图
  • 输入输出、耗时、Token 与错误
  • 筛选、聚合、评估和告警

我选择继续验证

让诊断结论可以被人核对

  • 先指出最早异常与候选原因
  • 每条判断都能回到原始证据
  • 保留反面证据，由人完成复核
技术成功 ≠ 业务正确报错节点 ≠ 首个根因AI 判断 ≠ 可信结论
选择依据：对 Agent 排障来说，数据更多不一定更快，可信的证据组织更重要
这是第一周最重要的产品判断。现有产品已经能把链路看得很细，我选择验证的是：能否先提出候选原因，同时要求每条判断引用原始证据和反证，再由工程师拍板。这个选择来自三点：技术成功不等于业务正确，最终报错点不一定是根因，AI 的判断也不能直接当答案。

03 做出选择 · 从判断到设计

07

第二周，我把这个判断
落实成三个可以检查的设计约束

01 · 先定位

给候选，不替人下结论

指出最早异常与 Top-3 候选 证据不足时明确说“不确定”
02 · 再核对

支持证据与反证同时出现

每条结论引用原始 Trace 确认、排除或补充证据
03 · 再沉淀

把确认过的问题转成回归

事故不只停留在一次排查 进入后续版本的回归检查
在部门业务中的位置

复用现有云原生可观测底座，补充 Agent 语义和诊断闭环，不另做一套孤立平台。

产品方案：“运行记录 → 事故诊断 → 证据复核 → 回归门禁”
第二周我用 14 项任务把判断落到流程、PRD、异常、测试和原型里。设计约束只有三条：不给绝对答案，所有结论可回查，同时让确认过的问题进入回归。对部门的定位也很清楚：它应该融入现有可观测平台，而不是再建一个独立系统。

04 验证答案 · 现场演示

08

我把产品判断做成“寻迹”，
让同事可以沿着真实任务检查它

发现事故
查看候选原因
核对支持与反面证据
转为回归检查
打开“寻迹”原型 ↗

演示只走一条主路径，约 1 分钟。

原型验证的是流程和产品判断，不代表已经接入生产系统
现场演示控制在一分钟。只走事故列表、诊断工作台、双向证据复核和回归门禁。不要介绍所有菜单。重点是请大家看产品判断如何变成界面和操作，而不是展示页面数量。

04 验证答案 · 反馈与修正

09

验证没有证明“我做对了”，
它先帮我发现哪里还不成立

同事走查后，我改了产品表达

  • 去掉“庭审、裁决”等角色隐喻，改成工程语言
  • 补充正常 Trace，避免产品只剩“事故列表”
  • 拆开步骤类型与故障类型，修正数据口径
  • 调整列表宽度、入口关系和页面布局

自我质疑后，我换了主案例

  • 最初案例“状态过期”容易展示
  • 但 TTL、变更订阅就可能低成本解决
  • 它不足以证明必须做证据化诊断
  • 改为“步骤都成功，业务结果仍错误”的复合问题

AI 的实际作用我先提出怀疑，让 AI 从反方拆解并提供候选；最终由我判断质疑是否成立，并承担修改方案的取舍。

截至中期，原型已经可讨论；但产品价值仍需用真实事故和真实平台能力验证
这页讲验证带来的真实变化。外部走查让我改了术语、数据口径和页面；内部自查让我推翻了第一版主案例。AI 提供反方和候选，但提出问题、接受不舒服的结论并决定修改，是我自己的判断。这也是两周里最重要的收获。

05 价值落地 · 产品能力演进

10

前两周回答“为什么做、做什么”，
后两周回到研发本行回答“怎么真正做出来”

Week 1 · 已完成

看懂问题

竞品研究、场景筛选、机会与可行性判断。

Week 2 · 已完成

设计答案

流程、PRD、原型、走查与自我修正。

Week 3 · 下一步

把答案写成代码

选择最小闭环，核对真实平台接口、数据和实现边界。

Week 4 · 下一步

用运行 Demo 验证

接入 1—2 条真实链路，评估价值、成本与误判风险。

关键目标

不是另做一个演示系统，而是把有价值的一小段设计放进部门实际产品迭代，在真实链路中接受验证。

最终形成可执行建议：接入现有平台、调整后再做，或暂不推进
后两周我会回到研发角色，但不会把产品判断丢掉。计划先与产品经理和研发同事核对现有平台，再选最小闭环写成代码，用一到两条真实链路验证。最重要的是推动设计进入实际产品迭代，而不是在旁边做一个更完整的演示系统。
