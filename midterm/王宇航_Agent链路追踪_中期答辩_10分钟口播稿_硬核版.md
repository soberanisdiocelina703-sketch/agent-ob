## 第1页｜封面（0:00—0:30）

各位领导好，我是平台产品技术部云原生部的王宇航。

我今天汇报的不是一个已经成立的产品结论，而是一轮14天的产品验证：我如何从不了解 Agent 链路追踪开始，判断它为什么值得研究、市场机会在哪里、应该解决什么问题，以及后两周准备用代码验证什么。

## 第2页｜14天成绩单（0:30—1:05）

先汇报结果。

第一周，我分析了三家核心竞品，评估五个候选场景，形成一个产品判断。第二周，我把判断拆成14项产品与设计任务，完成一个可点击原型，并经过三人走查和修改。

但需要先划清边界：这些产出证明我已经把问题和方案表达清楚，不证明它已经具备生产价值。生产价值要由真实事故、排障效率和接入成本来证明，这也是后两周的任务。

## 第3页｜01 看懂问题：项目为什么现在立项（1:05—2:00）

我的第一个结论是：Agent 链路追踪的需求，不是由技术概念推动的，而是由业务阶段变化推动的。

KC 等 Agent 业务早期主要验证功能是否可行；逐步进入实际使用后，关注点会转向四个运行问题：有没有异常、异常出现在哪一步、为什么产生、如何降低下一次重复发生的概率。

传统指标可以告诉我们整体是否变慢、变贵或者失败，日志可以记录局部事件，但 Agent 的一次结果通常由输入、上下文、模型、工具和多轮状态共同形成。缺少完整任务上下文时，单点信号很难回答“错误是怎么形成的”。

因此我的立项判断是：业务正从“建设 Agent”进入“运行和治理 Agent”，链路追踪是连接可观测数据和后续诊断治理的一层基础能力。

## 第4页｜01 看懂问题：Agent链路为什么更难（2:00—2:55）

第二个结论是：Agent 链路不是传统调用链换一个名字。

传统调用链路径相对稳定，异常往往体现为超时、报错或状态码；Agent 的路径会动态分支、循环、重试，步骤数量和输入上下文都会变化。

更关键的是，Agent 存在“静默失败”：所有模型和工具调用都返回成功，但最终业务结果仍然错误。最后一个输出节点只是暴露问题的位置，不一定是最早发生偏差的位置。

所以 Agent 链路追踪必须保留一次任务中的 Trace、关键 Span、输入输出、上下文版本和工具结果。它的目标不是多存数据，而是保留能够复盘因果过程的最小证据集。

## 第5页｜02 找到机会：竞品能力与空白（2:55—4:00）

我把三家产品放在一起研究，但没有把它们强行定义成完全同类竞品。

AgentLoop 更偏生产观测、评估、数据集和审计闭环；AgentArts 更偏开发、运行和观测一体化；Langfuse 更偏开放的 AI 工程平台和开发者生态。

三家产品说明，采集、Trace 展示、筛选、评估和成本分析已经是相对成熟的数据层能力。真正的问题是：当一次任务包含几十个 Span 时，用户仍然要在调用树、时序图和输入输出之间人工寻找首个异常，并判断哪些信息只是相关，哪些信息构成因果证据。

所以我识别的机会不是“竞品没有链路追踪”，而是“数据已经很多，诊断决策仍然依赖人工拼接”。从公开能力看，把首个异常、候选原因、支持证据、反面证据和人工复核组织成统一工作流，仍有验证空间。

## 第6页｜03 做出选择：产品判断与MVP边界（4:00—5:05）

基于这个机会，我选择验证“证据化诊断”，而不是再做一棵 Trace 树。

产品逻辑有三个约束：技术成功不等于业务正确；报错节点不等于首个根因；模型给出的相关性判断不等于可信结论。

因此，MVP 只做四件事：识别最早异常，给出不超过三个候选原因，每个原因引用可回跳的原始证据，同时给出反面证据，最后由人确认、排除或者要求补充数据。

我也明确了不做项：不自动修复，不自动定责，不把模型置信度包装成未经校准的百分比，也不重新建设一套 Trace 采集平台。

这个取舍的核心是信任。排障工具宁可少给一个证据不足的候选，也不能用一个看似确定、实际不可核对的答案消耗工程师信任。

## 第7页｜03 从判断到可执行设计（5:05—6:00）

第二周，我把判断落实成三段闭环。

第一段是定位：从运行记录和事故聚类进入诊断，默认展示最早异常和候选原因，原始 Trace 树保留为下钻能力。

第二段是复核：所有结论必须绑定原始事件引用；支持证据和反面证据同时展示。复核人只能选择确认、排除或补充证据，系统不替人拍板。

第三段是沉淀：只有人工确认的根因才能转成回归用例；早期门禁默认警告，不直接阻断发布，等误报率稳定后再决定是否升级。

在部门业务中，这应该是一层增量能力：复用现有云原生可观测底座和 Trace 数据，补充 Agent 语义、诊断和复核，不建设孤立平台。

## 第8页｜04 原型演示（6:00—7:05）

下面用一分钟展示这条主路径。

【打开“寻迹”原型，进入事故列表】

这里先按事故模式聚合异常运行，目标是减少用户在海量 Trace 中盲查。

【进入一条事故】

诊断页展示最早异常、候选原因和因果路径，但没有直接输出“唯一根因”。

【打开证据复核】

每条判断都可以回跳原始步骤；右侧同时显示反面证据。工程师可以确认、排除，或者标记证据不足。

【进入回归流程】

只有确认后的问题才能转为回归用例，避免把模型误判固化进发布流程。

这套原型目前验证的是信息架构和操作闭环，没有接入真实生产数据。

【返回汇报第9页】

## 第9页｜04 验证结果：哪些判断被推翻（7:05—8:15）

验证阶段最有价值的结果，不是页面完成，而是两个判断被修正。

第一类来自同事走查。“庭审、裁决”等表达增加理解成本，我改成直接的工程语言；正常 Trace 缺失会造成产品只处理异常的误解，我补充了完整运行记录；步骤类型和故障类型混用会污染数据口径，我重新拆分字段和筛选逻辑。

第二类来自对抗式自查。第一版主案例是状态或记忆过期，但这个问题可能通过 TTL 和变更订阅低成本预防，无法证明证据化诊断的必要性。

因此我把主案例改为检索排序漂移一类复合问题：检索、工具和模型步骤都可能成功，但多个条件组合后导致业务结果错误。这个场景更需要跨步骤证据比对，但它也更难实现，所以目前只能定义为待验证假设，不能说已经解决。

AI 在这里承担反方拆解和候选生成，我承担的是提出质疑、判断证据是否成立，以及决定是否推翻原方案。

## 第10页｜05 技术落地：后两周如何证伪（8:15—9:25）

后两周的目标不是把原型继续做大，而是尽快证伪三个核心假设。

第一，数据是否具备。我要核对现有平台能否稳定获得 Trace、Span、上下文版本、工具参数和结果等诊断所需字段。

第二，诊断是否有效。选择一到两类真实事故，验证首故障点 Top-3 命中率、证据引用完整率，以及工程师是否接受这些证据。没有标注样本时，不承诺命中率。

第三，价值是否覆盖成本。对比使用前后的平均排障时间，同时评估采集改造、存储查询、模型分析和人工复核成本。

技术实现上，第三周先完成最小数据映射和规则诊断；第四周接入一到两条真实链路，跑通“采集—诊断—复核”的 Demo。

最终输出不是“做得很完整”，而是一项决策：哪一段能力值得进入部门现有产品迭代，哪一段需要调整，或者当前证据不足、暂不推进。

## 第11页｜阶段结论（9:25—10:00）

14天前，我只知道 Agent 链路追踪这个名词。

现在，我形成了一项有边界的产品假设：基于现有 Trace 数据增加证据化诊断，可能降低复杂 Agent 问题的排查成本；但它能否成立，取决于真实数据完整度、诊断准确性和接入成本。

接下来我会回到研发本行，用代码和真实链路验证这三个条件，并推动经过验证的最小能力进入部门实际产品迭代。

我的汇报结束，谢谢各位领导。
