## 第1页｜封面（0:00—0:35）

大家好，我是平台产品技术部云原生部的王宇航。

我今天汇报的课题是 Agent 链路追踪。两周前，我对部门业务和这个概念都很陌生，只知道“Agent 链路追踪”这几个字。

所以今天我不准备把它讲成一次功能介绍，而是想汇报：在入职前14天里，我是怎样从看懂问题、分析机会、做出产品判断，走到方案验证，并准备回到研发完成技术落地的。

## 第2页｜14天成绩单（0:35—1:20）

先简单汇报一下这14天的阶段产出。

第一周，我比较了 AgentLoop、AgentArts、Langfuse 三家核心竞品，从五个候选场景里做取舍，最后形成了一个产品判断。

第二周，我围绕这个判断完成了流程、PRD、异常、测试和风险等14项设计任务，做出一个可点击原型，并请产品经理和研发同事共三人进行走查和修改。

这些数字说明任务完成情况，但我更想讲的是数字背后的过程：看懂、分析、判断、设计和验证。最后一步“落地”，目前仍在进行中。

## 第3页｜01 看懂问题：为什么值得做（1:20—2:20）

入职后的第一个挑战，不是马上开始做，而是先回答：这件事为什么值得做？

结合导师的建议和部门正在迭代的 KC 等 Agent 业务，我逐渐理解到，业务所处的阶段正在变化。

早期更关心 Agent 功能能不能做出来、流程能不能跑通、场景是否成立。随着 Agent 逐步进入实际使用，新的问题开始出现：上线后运行得怎么样？异常能不能及时发现？问题究竟发生在哪一步？排查时有没有足够的上下文？

所以，Agent 可观测和链路追踪并不是凭空出现的新概念。它背后的业务变化是：我们正在从“建设 Agent”，逐步走向“运行和治理 Agent”。这也是我理解的项目立项原因。

## 第4页｜01 看懂问题：Agent链路有什么不同（2:20—3:15）

我最初把链路追踪理解成“把调用过程画出来”。研究之后，我发现这个理解不够。

传统调用链主要帮助我们判断哪里慢了、哪里报错了。它的路径相对固定，问题通常会留下超时、报错或者状态码。

但 Agent 的执行路径可能分支、循环、调用多个工具，甚至每一步在技术上都成功，最后的业务结果仍然不对。

因此，Agent 链路追踪不仅要记录过程，还要保留输入、上下文、推理、工具调用和结果之间的联系。这样出问题时，排查者才能回到原始步骤，判断错误是怎样一步步形成的。

## 第5页｜02 找到机会：竞品之后还能做什么（3:15—4:20）

理解问题之后，我开始看市场上已经有哪些答案。

AgentLoop 在生产观测、评估、数据集和审计闭环上比较完整；AgentArts 更强调从开发、运行到观测的一体化；Langfuse 的开源、自托管和开发者生态更成熟。

这一步让我认识到，链路采集和 Trace 展示本身已经有很多成熟能力。如果只是再做一个类似的列表或者调用树，价值并不充分。

但从公开能力来看，面对大量 Trace 数据，工程师仍然需要自己在多个步骤之间反复核对。如何把最早的异常、候选原因、支持证据、反面证据和人工复核组织成一条统一的排障路径，我认为仍有继续验证的空间。

所以竞品研究对我最大的价值，不是整理了一张功能表，而是帮我把问题从“能看到链路”，进一步收敛到“能不能更快、也更可信地定位问题”。

## 第6页｜03 做出选择：我的产品判断（4:20—5:25）

基于前面的分析，我做出的产品判断是：不再增加一棵 Trace 树，先验证“证据化诊断”能不能降低 Agent 的排障成本。

这个判断来自三个不等式。

第一，技术执行成功，不等于业务结果正确；第二，最后出现问题的节点，不一定是最早的根因；第三，AI 给出的判断，也不等于可信结论。

因此，我希望产品先给出最早异常和少量候选原因，但不替工程师直接下结论。每条候选都必须能回到原始 Trace 核对，同时展示反面证据，最后由人确认、排除，或者要求补充证据。

我的选择不是让 AI 显得更聪明，而是尽量让排障者知道：这个判断为什么成立，又为什么可能不成立。

## 第7页｜03 从判断到设计（5:25—6:20）

第二周，我把这个判断落实成三个设计约束。

第一是先定位：给出最早异常和候选原因，但证据不足时必须明确说不确定。

第二是再核对：支持证据和反面证据同时展示，每条结论都可以跳回原始链路，由工程师完成复核。

第三是再沉淀：确认过的问题不只停留在一次排查，而是转成回归用例，在后续版本发布前再次检查。

这套方案在部门业务中的定位，也不是另做一个孤立平台。更合理的方式，是复用部门已有的云原生可观测底座，在上面补充 Agent 语义和诊断闭环。

## 第8页｜04 现场演示（6:20—7:30）

下面我用大约一分钟，演示这个判断如何变成具体产品流程。

【点击“打开寻迹原型”】

这里是事故列表。使用者先从异常运行进入具体事故，而不是从海量链路里盲目查找。

【进入一条事故】

系统给出最早异常和候选原因，但没有直接宣布根因。

【打开证据复核】

这里同时展示支持证据和反面证据，工程师可以回到原始步骤核对，并选择确认、排除或者暂时补充证据。

【进入回归流程】

只有经过人工确认的问题，才可以转成回归检查，避免把 AI 的错误判断固化进后续流程。

这就是原型的主路径：从发现事故、核对证据，到把一次排障沉淀为下一次发布前的检查。

【返回汇报第9页】

## 第9页｜04 验证答案：反馈与推翻（7:30—8:40）

做完原型以后，验证并没有证明“我做对了”，它先帮我发现了哪里还不成立。

在同事走查中，大家指出“庭审、裁决”等说法不符合工程工具的使用习惯，所以我全部改成了诊断、确认、排除等直接表达；有人提出正常 Trace 去哪里看，我补充了完整运行记录；还有同事指出步骤分类不通用，我重新拆分了步骤类型和故障类型，并修改了列表和页面布局。

更大的变化来自我对自己的质疑。第一版案例是“状态或记忆过期”，它容易理解，也容易演示。但继续拆解后，我发现 TTL、变更订阅等低成本手段就可能解决它，它不足以证明一定需要复杂诊断。

因此我推翻了这个案例，改为“每个步骤都成功，但业务结果仍然错误”的复合问题。

这里 AI 的作用，是在我提出怀疑后站在反方拆解并提供候选；是否接受质疑、怎样修改方案，最终仍然由我判断和负责。

## 第10页｜05 价值落地：后两周计划（8:40—9:30）

前两周，我主要回答了为什么做、做什么。后两周，我会回到研发本行，回答怎么真正做出来。

第三周，我计划先和产品经理、研发同事核对部门现有平台的接口、数据和能力边界，选择一个最小诊断闭环写成代码。

第四周，再接入一到两条真实链路，让 Demo 真正运行起来，验证它能不能降低排查成本，同时评估接入成本、误判风险和产品边界。

我希望后续不是在现有产品旁边再做一个演示系统，而是把其中有价值的一小段设计放进部门实际产品迭代，在真实业务中接受验证。最终给出接入、调整后再做，或者暂不推进的建议。

## 第11页｜阶段总结（9:30—10:00）

14天前，我只知道“Agent 链路追踪”这几个字。

现在，我能够说明它为什么在当前业务阶段值得研究，竞品留下了什么空间，我选择解决什么问题，以及这个判断怎样变成可以检查的产品设计。

我还没有完全看懂部门业务，但已经开始用业务的方式学习。接下来，我会把方案写成代码，并推动它进入实际产品迭代接受验证。

我的汇报结束，谢谢大家。
