    WEEK 1 · 任务 10

    差异化方向：Causal-first Debugger

    基于 AgentLoop 缺陷分析，5 个可感知差异落到具体设计

    # AgentLoop 现状与不足 寻迹 具体设计 用户第一眼的不同
    1 5 种 Trace 视图信息完整，缺统一诊断答案；认知切换多 诊断工作台为核心页面：症状、Top-3 候选、因果路径、证据入口集中一屏；Trace 树降级为底部按需下钻 打开事故先看结论候选，不是一棵几百节点的树
    2 STAROps / Judge 输出文本，无强制证据引用 证据卡片：每条候选根因挂支持证据与反证，每条证据引用 Span ID / 状态 Diff / 工具参数；无引用的结论不允许渲染 AI 说的每句话都能点进去验证，还主动给出「反对自己」的证据
    3 只能查看单条链路，判断「和正常的差在哪」靠人脑记忆 成功/失败 Diff：自动检索同类成功链，按状态、传参、工具三个维度并排对比，差异行高亮 像看代码 Diff 一样看两次执行的差异
    4 QuickStart 依赖链长、失败不回滚、无采集完整度反馈 接入体检：接入后自动出报告——字段覆盖率、断链数、重复 Span、敏感字段暴露，每项附一键修复指引 接完就知道「数据可不可信」，不等排障时才发现漏采
    5 Trace→评估→数据集→实验闭环完整，字段映射靠人工 三步闭环：打开事故（1）→ 复核（2）→ 转回归用例（3）；用例自动携带输入、上下文快照与期望不变量 从「看到问题」到「防住问题」三次点击
    不做"为了不同而不同"：产品仍使用工程后台常见的左侧导航、筛选表格、详情页、双栏对比和底部操作区。差异只放在信息顺序和证据约束上。排除：角色人格化名字、剧情式复核流程、大面积装饰动画、未校准的精确置信度百分比。

    WEEK 2 · 任务 3

    五层解决机制

    从「记录过程」到「防止复发」——每层都能独立落地，合在一起才构成闭环

    1

    数据层 — 先把过程记全

    通过标准探针（OTel）记录 Agent 每一步：调了哪个模型、用了哪个工具、读写了什么状态和记忆、把什么传给了下一步。给整条执行流水线装监控摄像头。

    OTel OTLP LangGraph 适配器 OpenAI Agents SDK Dify 采集端脱敏
    2

    因果层 — 把「先后」变成「因果」

    把执行记录连成因果图：哪一步写的状态被哪一步读了、上一步的输出成了下一步的输入。摄像头拍的是画面，因果图画的是「哪一步碰了哪一步」。

    因果图构建器 读写边分析 首故障点定位
    3

    证据层 — 规则抓现行，模型断疑案

    确定性问题（格式错、字段丢、状态过期）用规则直接判定；语义问题（检索排序漂移、多轮上下文冲突）交给模型——但模型必须指出具体证据，说不出来的结论不许上屏。

    4

    复核层 — 系统给证据，人做确认

    把「根因成立的理由」和「不成立的反证」摆在一起（诊断复核），由工程师复核。每次确认及理由都被记录，系统越用越准。

    5

    资产层 — 已确认的问题沉淀为防线

    每个确认根因的事故一键变成回归用例，下次发版前自动重跑，同样的坑不踩第二次。用例自动携带输入、上下文快照与期望不变量，无需字段映射。

    回归用例 发布门禁 CLI + Webhook 工具打桩回放

    信息架构（5 个主导航）
    寻迹

    ├─ 事故 → 失败模式簇 + 事故详情
    │　└─ 诊断工作台 → 证据 → Diff → 复核
    ├─ 回归与门禁 → 回归用例 + 发布检查报告

    └─ 设置 → 项目/成员/脱敏/告警
    设计原则：诊断工作台、Diff 与复核不是 3 个独立模块，而是事故详情内的连续子视图——避免一次排障被拆散成多个页面跳转。
    步骤级说明（关键决策点）
    步骤用户决策点输出
    1. 触发无（系统自动）新事故记录，归入失败模式簇
    2. 浏览运行查看哪次执行、是否筛选状态正常 Trace 详情或关联事故
    3. 事故列表先处理哪个簇（影响面排序辅助）选中一个事故
    4. 诊断工作台是否采信候选、看哪条证据理解「哪一步先出的错」
    5. 证据卡片证据是否充分形成个人判断
    6. Diff 视图差异是否解释失败确认或排除候选
    7. 复核（必选）确认是根因/排除该原因/暂需补充证据复核记录+校准信号
    8. 转用例用例归入哪个回归集回归用例（含脱敏快照）

    为什么这是克制的增强

    页面仍是「详情+双栏对比+底部操作」的工程后台结构，用户不需要学习新隐喻。变化只发生在：证据组织顺序 + 强制反证展示 + 结构化复核动作。

    复核状态机

    待复核
    ├─ 确认是根因 → 可生成回归用例
    ├─ 排除该原因 → 记录理由，可指向正确根因
    └─ 暂需补充证据 → 生成待补数据清单

    并发控制与反证处理

    后提交者收到「张工 2 分钟前已复核」提示，可选附议或重新复核——不静默覆盖。乐观锁用 candidate.version。反证区显示「未找到有效反证」——不能用空白暗示结论确定。

    WEEK 2 · 任务 6 + 9

    异常流程补全 + 测试覆盖

    数据/诊断/用户三侧 14 项异常处理 + 分层测试金字塔

    异常处理矩阵（14 项）
    数据侧（5 项）
    D-1 断链 Trace：启发式关联；失败挂孤儿区；体检给修复代码
    D-2 重复 Span：语义指纹去重；原始留档；体检指明来源
    D-3 字段缺失：该维度规则禁用标注「数据不足」；体检给补采指引
    D-4 超大 Trace：列表虚拟滚动；大字段存对象存储展示摘要
    D-5 敏感数据：采集端脱敏+服务端策略兜底；原文不落主库
    诊断侧（5 项）
    G-1 无候选根因：不编造结论；展示因果路径图+相似历史事故检索
    G-2 证据不足：候选降级为线索，折叠展示，复核入口禁用
    G-3 证据矛盾：标记「证据冲突」，强制走复核；冲突证据置顶

    WEEK 3 · 任务 2

    技术复盘：9 条设计问题反哺

    接口契约落地（11 个）过程中发现设计文档的不可行/不完整/含糊之处，按严重度分组

    P0 — 设计不可行（3 条）
    P0
    问题 1：Diff 基线推荐规则冲突
    原文：「最近 7 天同 Agent/版本/运行名称的成功链，按时间倒序取第一条」。实测：72h 内版本迭代 3 次，按时间最近的是 v1.4.2 成功链，但待诊断事故是 v1.4.0——版本不匹配，Diff 误导。
    修正：严格按版本匹配优先级高于时间；版本不匹配时明示「无同版本基线」而非静默推荐跨版本链。
    P0
    问题 2：复核并发控制缺 If-Match 载体
    原文：「乐观锁用 If-Match」，但未指明比对 candidates.version 还是 incidents.updated_at。前者单候选粒度，后者事故级——选错会导致候选 1 复核后候选 2 仍可无冲突提交。
    修正：用 candidates.version（整数自增）；incidents.updated_at 仅作展示，不作并发控制。
    P0
    问题 3：evidence_grade/incident_status 枚举未定义
    原文：多处字段无取值枚举；failure_type「单独定义」但未定义；regression_cases.suite_id 引用了未定义的 suites 表。
    修正：全部由本期实现单方面锁定（enums.py、candidates.version、补建 suites 表）；已回写 openapi.yaml。
    P1 — 设计不完整（6 条）
    P1
    问题 4：接入体检「字段覆盖率」口径不明
    原文：「字段覆盖率」未说明分母（OTel 全字段 vs GenAI 语义字段 vs 业务可选字段）。实现：分母为 GenAI 语义字段（12 个必填+8 个条件必填），按 Span 类型分组统计。
    P1
    问题 5：平台差异未覆盖（Bash vs PowerShell）
    原文：体检未提及平台矩阵检测。实测：headless 权限墙拦截后 Agent 真实改变策略（连拒 4 次后改用 Read 翻文件），产生「假失败 Trace」污染基线池。
    建议修改：docs/05 体检模块增补「平台矩阵检测+权限配置探测+权限拒绝事件独立分类（不计入故障统计）」。
    P1
    问题 6：诊断超时策略缺异步通道
    原文：「模型超时 30s」，但未说明超时后是轮询还是 WebSocket 推送。实现：规则先返回，模型结果用 Server-Sent Events 增量推送（avoid 30s 空白页）。
    P1
    问题 7：复核理由字段 max_length 缺失（实现：2048 chars）
    P1
    问题 8：回归用例 suite_id 外键未建表（实现：补建 suites 表）
    P1
    问题 9：failure_type 枚举声明「单独定义」但全文无定义
    实现：用 FM-01~FM-09 九类枚举值（CACHE_EXPIRED/FIELD_MISSING/...），已回写 schema.sql。

    6 项质量风险（Week 2 任务 13）
    高
    R-1 诊断误报导致信任崩塌
    缓解：规则先行；证据不足时降级为线索；反面证据常驻；发布节奏上先内部/设计伙伴使用
    高
    R-2 Diff 基线选择错误
    缓解：推荐的「成功链」与失败链任务语境不同，Diff 出的差异误导用户 → 兼容性规则前置（版本/运行名称/时间窗）；推荐依据明示；允许手动换基线
    中
    R-3 规则与模型结论冲突
    缓解：规则结果先渲染且不被模型覆盖；冲突时标记「证据冲突」强制走复核；用户复核校准模型阈值
    中
    R-4 敏感数据泄露
    缓解：采集端优先执行（正则掩码/哈希）；服务端策略兜底；原文不落主库且有审计记录；体检报告暴露项
    低
    R-5 回归用例快照过期
    缓解：快照超过 30 天显示警告；手动触发重录；不变量仍有效但上下文可能失效
    低
    R-6 并发复核数据竞争
    缓解：乐观锁用 candidates.version；后提交者看到先复核结果，选择附议或重新复核
