管理摘要 · 中期结论

02

方向值得进入真实场景验证，
但现在还不足以得出“应该接入”的结论

业务判断

需求正在变得真实

Agent 业务从功能探索进入实际使用，异常发现、问题定位与运行治理成为新课题。

产品判断

机会不在重复展示链路

Trace 数据已有较多成熟方案，仍需验证“首个异常—证据—复核”的诊断决策层。

阶段建议

小范围验证，再决定接入

用 1—2 条真实链路验证数据、效果与成本，形成接入、调整或暂停建议。

当前已完成

3 家竞品研究、5 个场景评估、产品方案、14 项设计任务、交互原型和 3 人走查。

中期重点不是证明方案正确，而是把下一步决策所需的关键假设说清楚
这一页先给领导结论。需求有业务背景，方向有研究价值，产品方案已经可讨论；但真实事故频率、诊断增量和接入成本尚未验证。因此建议进入小范围真实场景验证，而不是直接立项接入。[Sources] 第一、二周项目材料。

01 业务背景 · 为什么是现在

03

KC 等 Agent 业务逐步进入实际使用，
关注点从“建设”转向“运行与治理”

早期探索阶段

Agent 功能能不能做出来？

验证能力、跑通流程、确认业务场景是否成立。

逐步投入使用后

上线以后运行得怎么样？

异常如何发现、问题发生在哪一步、如何快速排查并避免重复发生。

立项依据

业务开始面对真实运行问题，需要把分散的指标、日志和执行步骤还原成一次完整任务。

Agent 链路追踪是 AI 可观测从“看见运行”走向“支持诊断与治理”的基础环节
业务阶段变化是项目立项的直接原因。早期关注功能可用，现在需要回答上线后的运行质量、问题定位和治理。这一变化使 Agent 可观测和链路追踪从概念研究变成实际业务课题。[Sources]《AI工程质量与安全_Agent 可观测与执行治理》；部门业务背景。

02 用户问题 · 排障为何仍然困难

04

真正的痛点不是“看不到 Trace”，
而是“看见以后仍然难定位”

当前常见排查路径

01
从告警或结果异常中找到目标运行
02
在调用树、时序、日志与输入输出间切换
03
人工比对上下文、工具参数与历史状态
04
凭经验判断最早异常与可能根因

Agent 场景新增难点

01
执行路径动态变化，存在分支、循环和重试
02
每一步都可能成功，最终业务结果仍错误
03
报错节点只是表象，偏差可能来自更早上下文
04
信息丰富，但缺少可核对的因果证据组织

产品目标：缩短从“发现异常”到“找到首个可验证原因”的路径。

技术成功不等于业务正确，是 Agent 排障区别于传统调用链的关键
目标用户是需要处理 Agent 运行问题的研发、测试、平台和 SRE 团队。现有工具能够展示大量信息，但用户仍需人工拼接因果关系。产品要解决的是诊断路径和证据组织，不是简单增加一个视图。[Sources] 第一周竞品分析与场景研究。

03 市场判断 · 竞品与机会

05

竞品的数据层能力已经较完整，
机会更可能出现在诊断决策层

AgentLoop

生产观测、评估、数据集与审计闭环较完整。

企业生产观测与治理

AgentArts

覆盖 Agent 开发、运行、托管与观测的一体化流程。

全栈开发运行平台

Langfuse

开源、自托管、评估与跨框架接入生态成熟。

开放的 AI 工程平台
成熟能力

Trace 采集、展示、筛选、评估、成本和基础告警。

机会假设

把首个异常、候选原因、支持证据、反面证据和人工复核组织成统一诊断工作流。

机会不是“别人没有链路追踪”，而是“数据很多，诊断仍依赖人工拼接”
三家产品定位并不完全相同，但共同证明数据层能力已相对成熟。下一步应验证的是诊断决策层能否提供可感知增量。这里基于公开能力形成机会假设，不做“竞品完全没有”的绝对判断。[Sources] 第一周竞品分析；各竞品公开文档研究结论。

04 产品定位 · 证据化诊断层

06

不重建 Trace 平台，
在现有可观测数据之上增加诊断决策能力

输入 · 复用底座

现有 Metrics / Logs / Traces

复用采集、存储、查询与权限能力 补充 Agent、模型、工具和上下文语义
处理 · 诊断组织

首个异常 + 候选原因

从大量 Span 中收敛关键路径 每个候选绑定支持证据与反证
输出 · 人机协同

人工复核 + 问题沉淀

由人确认、排除或补充证据 确认后转为后续回归检查
部门业务定位

作为现有云原生可观测平台的 Agent 增量能力，而不是新的独立产品烟囱。

产品主路径：运行记录 → 事故诊断 → 证据复核 → 回归检查
定位决定建设边界。底层采集和查询尽量复用部门能力，产品增量集中在 Agent 语义还原、候选原因、证据组织和人工复核。这样既能利用部门云原生积累，也能降低重复建设风险。[Sources] 第一、二周产品方案；部门业务定位。

05 MVP 方案 · 范围与边界

07

第一期只验证诊断增量，
主动收缩自动化和平台建设范围

P0 · 必须验证

让诊断结论可以被核对

  • 正常、异常和质量未评估的运行记录
  • 最早异常与不超过 3 个候选原因
  • 原始证据回跳、反面证据和人工复核
  • 确认后的问题可转为回归用例

第一期 · 明确不做

避免范围失控与信任透支

  • 不自动修复，不自动定责
  • 不展示未经真实数据校准的置信度
  • 不重建采集、存储和查询平台
  • 不替代团队现有 CI/CD 与发布系统
候选最多 3 个无证据引用，不展示先警告，暂不默认阻断
核心原则：证据不足时宁可少给候选，也不输出无法核对的确定答案
MVP 聚焦于验证诊断决策是否有增量。范围外包括自动修复、自动定责、完整平台底座和现有发布系统。主动收缩能够减少实现成本，也能避免模型判断尚未校准时透支工程师信任。[Sources] 第二周 PRD、设计决策与质量风险。

06 方案演示 · 寻迹原型

08

用一条主路径验证
产品定位与信息架构

从异常运行发现事故
查看首个异常与候选原因
核对支持证据与反证
人工确认后转为回归
打开“寻迹”原型↗

演示目标：验证流程是否清楚，不代表已接入生产数据。

现场演示控制在 1 分钟：事故列表 → 诊断 → 证据复核 → 回归
演示只走主路径。重点观察产品如何从大量 Trace 数据收敛到候选原因，又如何通过证据和人工复核控制模型判断风险。原型是信息架构和交互验证，不代表生产能力已实现。[Sources] 第二周可点击原型与设计文档。

07 阶段验证 · 证据与风险

09

当前已经验证“方案可讨论”，
尚未验证“产品有生产增量”

已形成的证据

  • 完成竞品、场景、方案、PRD 和交互原型
  • 产品经理与研发同事完成 3 人走查
  • 根据反馈修正术语、运行入口、分类和布局
  • 通过对抗式自查更换不够成立的主案例

仍待验证的关键假设

  • 真实事故是否高频且具有跨步骤诊断需求
  • 现有平台能否提供完整、可回跳的诊断数据
  • 候选原因能否缩短排障时间且不误导用户
  • 诊断增量能否覆盖采集、模型与人工复核成本

主要风险数据不完整、模型幻觉、误报导致信任下降，以及敏感输入输出的采集与权限边界。

中期边界：原型已完成；真实诊断效果和商业价值均未形成结论
阶段证据支持继续验证，但不支持直接进入生产。走查证明流程可以被理解，自查暴露了案例选择风险；仍需真实事故、真实平台数据和排障对比才能判断产品增量。[Sources] 第二周评审反馈、用户走查、设计决策与质量风险。

08 部门融合 · 四周推进计划

10

从独立方案验证，
逐步收敛为现有平台的一段增量能力

Week 1 · 已完成

机会判断

竞品研究、场景筛选、定位与可行性分析。

Week 2 · 已完成

方案表达

流程、PRD、原型、走查、风险和边界。

Week 3 · 待推进

最小技术闭环

核对平台接口与字段，完成数据映射和规则诊断。

Week 4 · 待推进

真实链路验证

接入 1—2 条真实链路，评估效果、成本和边界。

融合原则

优先进入部门现有产品迭代，以模块或能力方式接入；不在平台之外继续扩建独立演示系统。

推进方式：先验证最小增量，再根据数据决定是否扩展能力范围
Week 3 和 Week 4 的工作需要与实际产品迭代对齐。先核对现有平台能提供什么数据，再实现最小诊断闭环，最后用真实链路验证。只有验证通过的能力才进入产品排期。[Sources] 项目后两周计划；部门业务定位。

09 决策建议 · 下一步

11

中期建议：进入真实链路验证，
通过三项门槛后再决定是否接入

数据门槛

字段完整、链路可回跳

Trace / Span、上下文和工具结果能稳定获取。

效果门槛

诊断对排障有增量

候选原因可接受，证据完整，排障时间有改善。

成本门槛

收益覆盖总接入成本

综合评估采集、存储、查询、模型和人工复核。

最终输出一项明确产品决策：接入现有平台 / 调整方案后再做 / 当前证据不足，暂不推进。
