# Agent 链路追踪产品设计与原型交付 Prompt(第二周·优化版)

## 你的角色

你是一名兼具产品设计、交互设计、系统架构和测试架构能力的资深产品负责人。你的任务不是罗列功能,而是把第一周研究得出的结论,落成一套「可以拿去评审、拿去开发、拿去演示」的产品设计交付物,形成一条完整的设计证据链:

> 选定场景 → 核心流程 → 差异化落地 → PRD 与边界 → 异常与容错 → 设计稿与可点击原型 → 技术草图 → 测试与质量风险 → 可用性验证与迭代 → 微交互与情感化 → 设计决策依据

所有设计必须能回溯到第一周的研究结论;不允许凭空新增没有论证的方向。不要使用「赋能、抓手、全方位、极致体验」等空泛表述。

## 前置输入(第一周已确定的结论,不得推翻,只能细化)

来自 `first-week/agent-tracing-competitive-analysis.md`:

1. **选定场景：** Agent 多步骤执行中的因果故障定位与证据化回放。数据层保留 conversation、root_run、parent_run 等层级，覆盖多步骤执行并为多 Agent 协作场景留位。
2. **主差异化方向:** Causal-first Debugger(因果优先调试器)。产品主张:「不只是告诉你发生了什么,而是给出最早的故障因、完整证据和验证办法。」
3. **可感知差异:** 打开事故即看到候选根因(Top-3)、影响路径、证据、反证、与成功执行的 Diff。
4. **对标竞品缺口(AgentLoop):** 五种 Trace 视图信息丰富但认知切换多;缺少「症状 → 候选根因 → 证据 → 验证动作」的统一诊断工作台;Session 多轮能力不完整;接入依赖链长且无体检;闭环跨模块操作多。
5. **MVP 边界(必须做):** OTel 接入 + 2–3 框架适配;Agent 语义事件(task/handoff/state diff/memory/artifact lineage);运行记录（成功/失败）+ 正常 Trace 详情 + Trace 树 + 因果图 + 成功/失败 Diff;规则/不变量 + 轨迹模型的候选根因;证据卡片、人工确认与转回归用例。
6. **明确不做:** 通用 APM、完整 Prompt 管理、低代码 Builder、自动修改生产 Agent、全量模型网关、第一期全框架全语言全云。
7. **技术底座:** OTel/W3C Trace Context 采集,ClickHouse 观测存储,因果图构建器,规则/不变量引擎 + 轨迹评估器,诊断必须引用具体事件并支持人工确认/驳回。
8. **核心验证指标:** 首故障点 Top-3 命中率、证据接受率、MTTR 降幅、同类问题复发率。

## 设计原则(贯穿所有交付物)

1. **结论先行:** 每个界面先给「结论候选 + 证据」,再允许下钻原始 Trace;不让用户在海量 Span 里自己找答案。
2. **证据可追溯:** 所有 AI 结论必须引用具体 Span ID、状态 Diff、工具参数或制品版本,并同时给出支持证据、反对证据和证据等级;无证据的结论不许出现在界面上。
3. **人是最终复核者:** AI 只输出候选诊断;确认、驳回、重新复核都由人完成,且反馈用于校准。不做自动定责、不做自动修复。
4. **三步闭环:** 从「发现问题」到「生成回归用例」不超过三次主操作。
5. **确定性优先:** 规则/不变量能判定的问题不交给模型;模型只处理语义与因果排序。
6. **主流模式优先:** 原型先遵循成熟工程后台的导航、列表、详情、对比和确认模式;创新必须直接降低排障成本,不使用角色扮演、剧情化术语或装饰性视觉来制造新奇感。

## 必须完成的设计任务

以下 14 项任务与 `prompt.md` 的 14 项任务一一对应,每项都必须单独成节输出,不得合并、不得遗漏。

### 任务 1:核心流程设计

对应原始任务:「核心流程设计:基于第 1 周选定场景,画出核心流程」。

围绕选定场景画出产品核心流程,要求:

- 一条主流程:告警/低分触发 → 事故聚类 → 打开诊断工作台 → 查看首故障点与证据 → 复核 → 转回归用例 → 实验验证 → 门禁放行;
- 用 Mermaid 或等价文本流程图表达,节点要对应到具体页面/模块;
- 标注每一步的输入、输出和用户决策点;
- 给出页面级信息架构(站点地图),说明页面之间的跳转关系。

### 任务 2:Demo 输出(原型设计稿)

对应原始任务:「Demo 输出:原型设计稿/可交互 Demo(可用 AI 工具)」。

在动手写可点击原型(任务 7)之前,先输出页面级设计稿,作为原型的蓝图:

- 对主流程涉及的每个页面,给出一份「页面设计稿」;必须包含运行记录和正常 Trace 详情,正常 Trace 不显示诊断区:页面名称、页面目标、区块划分(布局示意可用文本/ASCII 结构图)、每个区块承载的信息与控件、主操作与次操作;
- 标注每个页面的「第一眼要素」——用户打开页面 3 秒内必须看到的结论性信息(呼应设计原则 1);
- 说明页面间的数据传递(从事故列表进入工作台带什么上下文,从工作台转用例带什么字段);
- 设计稿与任务 1 的站点地图页面一一对应,与任务 7 的原型页面一一对应;
- 可以使用 AI 工具辅助生成,但最终稿必须收敛为文档中的明确描述,不能只留一句「见原型」。

### 任务 3:产品方案说明

对应原始任务:「产品方案说明:用自己的话讲清楚『为什么解决什么问题、怎么解决』」。

用自己的话讲清楚三件事,每件不超过半页:

- **为什么:** 谁在什么情况下痛,痛的代价是什么(引用第一周证据);
- **解决什么问题:** 一句话场景定义 + 三个可衡量的价值指标;
- **怎么解决:** 用「数据 → 因果 → 证据 → 复核 → 资产」五层说明产品机制,让不懂技术的人也能听懂。

### 任务 4:差异化设计落地

对应原始任务:「差异化设计落地:把第 1 周定的差异化方向具体体现在设计里」。

把 Causal-first Debugger 的差异化逐条落到具体设计上。对每个差异点说明:

- 竞品(AgentLoop)当前的做法与不足;
- 我们对应的具体界面/交互/机制设计(要能在原型里指出来);
- 用户第一眼能感知到的不同是什么。

至少覆盖:诊断工作台 vs 五视图切换、证据卡片 vs 纯文本总结、成功/失败 Diff vs 单链路查看、接入体检 vs 裸接入、三步闭环 vs 跨模块跳转。

### 任务 5:PRD 撰写

对应原始任务:「PRD 撰写:功能、流程、边界说清楚」。

按模块写清功能需求,每个功能包含:

- 用户故事(谁、想做什么、为了什么);
- 功能描述与交互要点;
- 输入 / 输出 / 数据对象;
- 边界条件与明确不做项;
- 优先级(P0 / P1 / P2)与验收标准。

模块至少包含:接入与采集体检、运行记录与正常 Trace 详情、事故列表与失败模式聚类、因果诊断工作台、成功/失败 Diff、证据复核与反馈、回归用例与发布门禁、基础设置与权限。

运行记录和事故列表必须采用三层通用口径:Agent / 运行名称用于标识业务,步骤类型使用跨框架稳定枚举,步骤名称保留接入方原始业务语义;故障类型单独定义。不得把某个演示案例中的「退款执行」等业务节点写成全局步骤分类。

### 任务 6:异常流程补全

对应原始任务:「异常流程补全:补容错和异常设计」。

对每个核心模块补全容错与异常设计,至少覆盖:

- 数据侧:断链 Trace、重复 Span、字段缺失、超大 Trace、敏感数据;
- 诊断侧:无候选根因、证据不足、证据互相矛盾、模型超时/失败;
- 用户侧:误复核要重新复核、并发复核冲突、权限不足、空状态与首次引导;
- 每个异常给出:触发条件 → 系统行为 → 用户可见文案 → 恢复路径。

### 任务 7:可点击原型

对应原始任务:「可点击原型:做完整可点击交互原型」。

依据任务 2 的设计稿,制作一个可直接双击打开的单文件 HTML 交互原型:

- 覆盖主流程全部页面,页面间可点击跳转,走得通「发现 → 诊断 → 复核 → 转用例 → 门禁」全流程;
- 使用贴近真实且类型多样的模拟数据（同一 Agent 中覆盖状态、契约、工具、检索、模型输出和编排事故）,不用 Lorem Ipsum;
- 关键交互可操作:筛选、展开证据、复核确认/驳回、Diff 对比、生成回归用例;
- 异常状态至少演示 2 个(如证据不足的诊断、断链警告),与任务 6 的异常设计对应;
- 不依赖联网资源,CSS/JS 全部内嵌;桌面端优先,布局整洁专业;
- 产品顶部提供「快速排障引导」,让第一次打开的人知道点击路径。

### 任务 8:技术方案草图

对应原始任务:「技术方案草图:基于第 1 周可行性预判,输出技术实现草图(架构/接口/数据结构)」。

基于第一周可行性预判细化,不推翻既有选型:

- 高层架构图(采集 → 传输 → 存储 → 因果构建 → 诊断 → 界面);
- 核心接口草案:OTLP 接入、运行记录、Trace 详情、事故列表、诊断结果、复核反馈、回归用例导出等 5–10 个关键 API 的方法、路径、请求/响应要点;
- 核心数据结构:沿用第一周的 Trace/Step/Handoff/State/Memory/Tool/Artifact/Diagnosis 对象,细化到字段级别并说明索引与存储位置;
- 说明规则引擎与轨迹模型的分工边界和调用时序。

### 任务 9:测试用例设计

对应原始任务:「测试用例设计:针对设计方案,输出测试用例(覆盖核心流程、异常、边界)」。

针对设计方案输出测试用例,要求:

- 覆盖核心流程(正向路径)、异常流程(任务 6 的异常)和边界条件(空数据、超大数据、并发、权限);
- 每条用例包含:编号、模块、前置条件、步骤、预期结果、优先级;
- 单独一组「诊断质量」用例:用已知根因的事故集验证 Top-3 命中率、证据引用完整性、证据等级校准;
- 用例总数不追求多,但 P0 功能必须每条验收标准都有对应用例。

### 任务 10:设计评审与用户验证

对应原始任务:「可用性测试:找 3 人测原型并迭代」。

把已经发生的项目评审和后续正式任务测试分开记录：

- 实际收到的反馈必须保留日期、原话、问题判断、修改位置和核验结果；
- 正式任务覆盖首故障点定位、证据回跳、复核转用例、采集可信度判断，以及证据不足的异常态；
- 只有实际参与的人才计入参与者人数，只有实际计时才填写耗时；
- 尚未执行的 3 人任务测试保留脚本和空白记录表，并明确完成条件；
- 用户验证文档要形成“证据—问题—修改—验证—剩余风险”闭环。

### 任务 11:微交互 / 情感化设计

对应原始任务:「微交互 / 情感化设计:关键节点的动效反馈&品牌情感化表达」。

为关键节点设计动效反馈与品牌情感化表达,要求服务于「让用户信任诊断结论」这一核心,不做装饰性动画:

- 挑出 4–6 个关键情感节点,至少覆盖:复核确认(确认根因的那一刻)、复核驳回、回归用例生成成功、门禁放行/警告、空状态与首次引导、诊断加载中;
- 每个节点用统一结构描述:触发时机 → 动效/反馈形式(时长、缓动、视觉变化) → 传达的情绪与目的(如「确认根因时的落定感」「证据不足时的克制提示」);
- 品牌情感化表达:定义产品的语气原则(如「像可靠的资深工程师,不夸张、不卖萌」),体现在关键文案(成功/失败/空状态/错误提示)、色彩语义(确认/驳回/警告的用色)和图标风格上;
- 所有动效必须在任务 7 的原型中真实可感(CSS/JS 实现),不能只写文字描述;动效时长克制(建议 150–400ms),不阻塞操作。

### 任务 12:设计说明 / 决策文档

对应原始任务:「设计说明/决策文档:阐述设计决策及依据」。

记录关键设计决策,每条用统一结构:

> 决策点 → 备选方案 → 选择 → 依据(回溯到第一周哪条结论/证据) → 代价与风险

至少覆盖:为什么以诊断工作台为核心页面而不是 Trace 列表、为什么证据卡片强制引用原始事件、为什么复核是必经步骤、为什么先做 3 类确定性故障、为什么门禁默认只警告不阻断。

### 任务 13:质量风险前置评估

对应原始任务:「质量风险前置评估:从测试视角提前指出方案的质量风险点」。

从测试视角提前指出方案的质量风险,每条包含:风险描述、影响面、发生概率(高/中/低)、探测手段、缓解措施。至少覆盖:诊断误报导致信任崩塌、Diff 基线选择错误、采集数据不完整导致证据链断裂、大 Trace 下的性能退化、复核反馈被污染。

### 任务 14:克制的设计增强

对应原始任务的创新要求,但执行时以「主流模式上的克制增强」为准。

设计 1 个围绕诊断可信度的克制增强,要求:

- 先沿用主流工程产品的页面结构和交互习惯,再增强证据组织或反馈质量;
- 与因果诊断的核心价值强相关,不是装饰性彩蛋,不引入剧情化角色、仪式或视觉隐喻;
- 说明增强解决什么问题、如何降低误判、用户如何使用,以及为什么不会增加学习成本;
- 必须在可点击原型中真实可用,不能只停留在文字描述。

## 输出物

在 `second-week/` 目录生成一套可逐项评分的提交材料：

1. `README.md` —— 大模型评分入口，列出 14 项任务、状态和证据；
2. `docs/tasks/01–14` —— 每个任务一份独立 Markdown，包含输入、产出、核验和剩余风险；
3. `docs/specs/ui-design-spec.md` —— 字体、字号、颜色、间距、组件、响应式和可访问性；
4. `docs/evidence/` —— 实际反馈、未决问题和验证记录；
5. `agent-tracing-prototype.html` —— 唯一的可点击产品原型（单文件、离线可开）；
6. `xunji-overview.html` 与 `assets/` —— 评审总览、流程图和技术架构图。

### Markdown 文档要求

- 开头提供不超过一页的「方案摘要」:产品一句话定义、核心流程一张图、三个差异化要点、最大风险;
- 有目录;文档章节按任务 1–14 的编号组织,读者能逐项对照 `prompt.md` 检查完成度;
- PRD 用表格表达功能清单,流程用流程图,决策用统一结构;
- 与第一周文档交叉引用时注明章节号;
- 文末列出「本期未决问题与下期验证项」。

### HTML 原型要求

- 单文件、内嵌 CSS/JS、离线可开、无外部依赖;
- 视觉风格专业稳重,优先采用主流 SaaS 后台的一贯模式(清晰侧栏、标准卡片、常规无衬线字体、克制语义色),再在关键诊断信息上做增强;
- 数据、诊断结论、证据、证据等级全部使用与设计文档一致的同一套模拟案例;成功与失败 Trace 必须在运行记录中同时可见;
- 每个页面有明确标题与导航高亮;不可用的功能显示禁用态而不是假装可点;
- 页面结构与任务 2 的设计稿一致,出现偏差时以文档为准并回改文档或原型,保持两者同步。

## 写作标准

- 简体中文;首次出现的英文术语附中文解释;
- 先说结论,再给依据;语言朴实具体,像给老板和开发同时讲清楚一件事;
- 功能描述精确到「用户点什么、看到什么、系统做什么」,不写「支持强大的 XX 能力」这类话;
- 文档与原型的信息必须一致:原型里出现的每个页面在 PRD 里都有对应模块,PRD 里的 P0 功能在原型里都能点到。
