# 第二周提交物 README 框架

> 项目根目录放一个 `README.md`。评分方是 AI，它顺着 README 从上到下读一遍就要能形成完整判断：为什么值得做 → 做了什么 → 凭什么比别人好 → 怎么做到 → 做到什么程度。
> 找不到、没写出来的东西，一律按没做处理。
>
> 本文分三部分：结构总览 → 可直接抄的模板 → 各章节写法与扣分点。

---

## 一、结构总览

```text
README
├── 1. 一句话项目介绍     ← 让 AI 10 秒知道你在干嘛
├── 2. 背景与痛点         ← 为什么值得做
├── 3. 用户与场景         ← 给谁解决什么问题
├── 4. 核心功能           ← 做了什么
├── 5. 核心创新           ← 为什么比别人好（差异化 + 创新点，分开写）
├── 6. 核心 Demo 流程     ← 应该怎么看你的项目（含任务—证据对照表）
├── 7. 技术实现           ← 怎么做到
├── 8. 完成度             ← 做到了什么程度（含能力状态、用户验证、AI 声明）
├── 9. 后续规划           ← 未来空间
└── 10. 亮点总结          ← 给 AI 一个最终答案
    └── 附：与第一周衔接、目录结构
```

## 三、各章节写法与扣分点

### 2. 背景与痛点
三层里第三层「为什么现在还没被解决」是拉开分差的地方。只写"效率低、体验差"会被判为通用表述，价值性拿不到高等级。

### 3. 用户与场景
目标用户写成"所有需要 xx 的人"等于没写。**非目标**这一条很多人漏，但它直接对应严谨性。

### 4. 核心功能
不要平铺罗列。每个功能都要能对上第 2 节的某个痛点，对不上的会被判功能堆砌。"本期不做什么"必须写——PRD 缺非目标，严谨性最高 2 级。

### 5. 核心创新
差异化和创新是两个独立任务（第 4 项 60 分、第 14 项 80 分），必须分开写。如果是同一个设计点，要分别说明它在两处各证明什么，否则按重复收割只算一项。
5.2 的最后一项「副作用与适用边界」不写，创新等级最高 3 级。

### 6. 核心 Demo 流程
这一节是所有证据的定位入口。任务—证据对照表最后一列必须写：第 6/9/13 项分别是设计层、验证层、风险层，第 4/14 项是"和竞品不一样"与"超出常规"，不说明各自证明什么，会被合并算一项。
表里宁缺勿虚，没做的项不填。

### 7. 技术实现
只写 `React + Node + LLM + RAG` 而不解释为什么这么选、怎么实现、哪一步最可能失败，是典型低分。接口要写**失败返回**，AI 接入要写**失败兜底**。

### 8. 完成度
四类状态必须分开标：已实现 / 仅设计稿 / 规划未实现 / 作者假设。这是防「说到没做到」被扣真实性的关键——文档里写了但 Demo 里找不到，真实性最高 2 级，整项封到 70%。
用户测试：AI 模拟用户不计入真实用户；虚构记录该项直接 0 分。
AI 声明：主动说清 AI 用在哪、自己改了什么，不扣分；成品完整但说不清自己做了什么判断，才扣。

### 9. 后续规划
写"下一步最小验证动作"比写宏大路线图更有效。

### 10. 亮点总结
每条都要指向前面出现过的章节或文件，不要引入新说法。

### 附一：第一周衔接
无说明地推翻第一周结论会扣逻辑性，说明清楚不扣分。

### 附二：目录结构
`docs/` 文件名带任务编号，让 AI 零成本完成任务定位。

---

## 四、五条注意

1. README 是叙事主干 + 证据入口，详细内容写进 `docs/`。README 写得很完整但源码对不上，会被判为高度依赖 AI。
2. 第 4、5、7 节提到的每个能力，都要能在第 8 节的状态表里找到状态，或在文件中指到位置。
3. 「设计了」不要写成「已实现」，「预计效果」不要写成「实际效果」。
4. 第 6 节的任务—证据对照表宁缺勿虚。
5. 全篇不要出现前后不一致的字段名、状态名、流程步骤——README、PRD、原型、源码四处会被交叉比对。
