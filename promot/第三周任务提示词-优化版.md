# 寻迹（Agent 链路诊断）工程实现 Prompt（第三周·优化版）

## 你的角色

你是一名兼具系统架构、后端开发、前端开发和测试能力的资深技术负责人。你的任务不是重新设计产品，而是把第二周已评审通过的产品方案，落成一套「可以拿去运行、拿去测试、拿去复盘」的工程交付物，形成一条完整的实现证据链：

> 产品方案 → 技术架构与选型 → 接口与数据契约 → 核心流程代码 → 单元测试 → 端到端 Demo → 技术复盘反哺产品

所有实现必须能回溯到第二周的设计结论（`second-week/docs/01–14`）；不允许凭空新增没有设计依据的功能。凡实现与设计冲突之处，不得静默改设计——记入任务 6 的技术复盘。

## 前置输入（第二周已确定的结论，不得推翻，只能细化和取舍）

1. **产品定义（docs/03）：** 为运行 Agent 生产系统的团队解决「报错步骤不等于根因步骤」的问题，机制为「数据 → 因果 → 证据 → 复核 → 资产」五层。
2. **核心流程（docs/01）：** 运行记录 → 事故列表（失败模式聚类）→ 诊断工作台（首故障点 + Top-3 候选 + 证据等级）→ 证据卡片（支持证据/反证/原始事件跳转）→ 成功/失败 Diff → 诊断复核（确认/排除/证据不足，必选其一）→ 一键转回归用例 → 发布门禁（默认警告不阻断）。
3. **目标架构（docs/08）：** OTel/OTLP 采集 → 接入网关 → 消息队列 → 标准化器 → ClickHouse 观测存储 + 因果图构建器 → 规则/不变量引擎（同步，毫秒级）+ 轨迹评估模型（异步，秒级）→ 诊断聚合 → Postgres 业务库 → Web 前端 + 门禁 CLI。
4. **接口契约（docs/08 §8.2）：** `POST /v1/traces`（OTLP 标准路径）、`GET /v1/projects/{pid}/traces`、`GET /v1/traces/{tid}`、`GET /v1/projects/{pid}/incidents`、`GET /v1/incidents/{iid}/diagnosis`（含 SSE 增量通道）、`GET /v1/incidents/{iid}/diff?baseline=`、`POST /v1/candidates/{cid}/review`（If-Match 并发控制）、`POST /v1/incidents/{iid}/regression-case`（仅 confirmed）、`POST /v1/suites/{sid}/gate-run`（warn|block）。
5. **数据结构（docs/08 §8.3）：** 观测侧 `spans / events_state / events_handoff / events_memory`；业务侧 `incidents / failure_clusters / diagnoses / candidates / evidence / verdicts / regression_cases / gate_runs`。硬约束：每条 evidence 的 `span_ref` 或 `event_ref` 至少一个存在；`raw_score` 不直接展示；复核枚举 `confirmed | excluded | insufficient` 在 API 与库中一致。
6. **规则与模型分工（docs/08 §8.4）：** 确定性问题（Schema 校验、必填字段、状态过期、数值约束）由规则引擎判定；语义问题（因果排序、反证搜集）由模型处理，且模型结论必须是结构化证据引用。时序：规则结果先渲染，模型结果异步增量推送，模型失败不阻塞页面。
7. **异常设计（docs/06）：** 断链 Trace、字段缺失、无候选根因、证据不足、模型超时、并发复核冲突等，实现中至少覆盖其中与核心流程直接相关者。
8. **质量口径（docs/03 §3.6）：** 首故障点 Top-3 命中率、证据接受率、处置时间是产品验证指标；本周 Demo 用「已知根因的样例事故集」验证前两项可测。

## 本周范围裁定：通用流优先（T1/T2 分级）

实现前评估确认：state/handoff/memory 语义事件**不是行业通用约定**——OTel GenAI 语义约定只覆盖模型调用、工具调用级的 Span 语义；「状态」「交接」是 LangGraph、OpenAI Agents SDK 等特定框架的原生概念，在 Claude Code 等无状态图框架的通用事件流中无法自动获得。据此对第一期产品主张做如下裁定（这是对前置输入第 5、6 条的取舍，不是推翻——表结构与分工原则保留）：

- **T1 通用流诊断（本周实现与演示的全部范围）：** 只依赖任何框架都能自动采集的数据——Span 树、模型/工具调用及其输入输出、时序、错误。可判定的故障：工具参数 Schema 违例、步骤输出契约违例（格式错误/必填字段缺失）、异常与超时传播、检索空结果，以及**成功/失败 Diff 对照**发现的首个分歧点。因果图相应退化为「父子层级 + 时序 + 数据流启发式（上游输出出现在下游输入中）」。
- **T2 深接入增强（本周只保留定义，不实现、不演示）：** state/handoff/memory 语义事件、状态过期等依赖它们的规则、注解 API 的上报链路。建表与接口定义保留并标注 T2，未来由状态原生框架适配（LangGraph 等）或接入方注解补齐。
- **差异化叙事同步收窄：** 本周「首故障点定位」的依据是 T1 证据 + Diff 对照，不宣传状态级因果回溯；证据卡片的「反证」主要来源是成功基线对照与替代解释，不承诺状态链反证。此决策及其对第二周 docs/03（五层机制）、docs/04（差异化）叙事的连锁影响，必须作为任务 6 反哺清单的第一条。

## 工程原则（贯穿所有交付物）

1. **目标架构与 Demo 架构分离但同构：** 生产选型（ClickHouse、Kafka、Postgres）本周不真实部署；Demo 用轻量替身（SQLite/内存队列/单进程），但**接口路径、数据字段、枚举值必须与目标架构逐字一致**，替换的只是存储和传输实现。每处简化都要写明「目标形态 → Demo 形态 → 升级路径」。
2. **真实数据主路径：** Demo 的核心流程必须由真实 Agent 工作负载现场驱动——通过本地 Claude Code CLI（`claude -p --output-format stream-json`）执行真实多步骤任务，经产品接入层实时转入后台。手工维护的 fixtures 只充当单元测试与离线 CI 的夹具，且必须由真实运行录制转换而来。代码库禁止出现任何预写的诊断候选、证据文案或复核结论——所有上屏内容必须是运行时计算产物，评分者应能通过改动故障注入参数改变诊断结果来验证这一点。
3. **确定性优先，模型可插拔：** 规则/不变量引擎是本周实现的重心，必须真实可跑；轨迹评估模型封装为可插拔接口：默认启发式 Mock（离线 CI 用），可选 `ClaudeCodeEvaluator` 适配器（子进程调用本机已登录的 Claude Code 做真实语义诊断）。离线态下 Mock 兜底，保证无网环境仍能跑通全流程。
4. **证据强制引用：** 诊断候选在代码层面强制携带证据引用（span_ref/event_ref 至少其一），违反约束的候选在聚合层直接丢弃并记日志——这是产品设计原则 2 的代码化。
5. **端到端优先于单点完美：** 先打通「样例 Trace 入库 → 事故生成 → 诊断 → 复核 → 转用例 → 门禁」的最小闭环，再回头加厚单点；任何一步不可运行，整周交付即不合格。
6. **实现即复盘素材：** 编码中每次发现设计文档说不清、做不了、有矛盾的地方，立刻记入 `retro-log.md`（一行一条：日期、位置、问题、临时决定），作为任务 6 的原始素材，不靠周末回忆。

### 任务 3：核心功能编码

对应原始任务：「实现产品核心流程的可运行代码」。

按端到端顺序实现，每个模块完成后即有可验证的中间产物：

1. **示例 Agent（真实数据源）：** 实现一个贴近真实企业用法的「读-析-报」工作负载——通过本地 Claude Code CLI（`claude -p`）或 Agent SDK 驱动真实模型执行多步骤任务，如「拉取账单明细与支付流水两份数据 → 逐项交叉核对 → 汇总差异 → 生成对账报告」（只读分析 + 低风险写报告，不含退款等高危自主操作，高危写操作在真实企业中必经人工审批，不进演示场景）；内置故障注入开关（如 `--inject stale-source | broken-contract | bad-tool-args`）：数据源工具返回过期缓存副本（报告数字错但全程无报错——静默质量故障，由对账校验步骤检出并触发事故）、上游步骤产出的中间文件缺必填字段（下游数步后才失败）、污染输入数据诱发模型传出违例工具参数。注入只允许实现在工作负载自有的工具与数据层，**不修改 Claude Code、不改动任务提示词**——正常与注入运行使用同一提示词，差异只来自环境；示例 Agent 不使用任何注解 API——它必须证明 T1 主张：仅凭通用事件流即可完成上述三类诊断；
2. **接入层（产品组件，对应第二周架构图的「框架适配器」）：** 目标体验是「接入方一次接入，后台自动收到监控数据」，提供两种方式：
   - **SDK 探针包**（`xunji-sdk`）：供 Agent SDK（`claude-agent-sdk`）开发者在源码中导入，包装 `query()` 消息流与 hooks，自动捕获每次模型请求与工具调用并上报 `POST /v1/traces`；
   - **Claude Code CLI 接入**：`xunji connect` 命令自动向 `settings.json` 写入 PreToolUse/PostToolUse hooks 实现旁路上报，零代码改动；headless 场景提供 `xunji run -- claude -p "..."` 包装命令解析 `stream-json`；
   - 两种方式共用同一事件重建逻辑：重建 Span 父子关系与每步输入输出；注解 API（`log_state_write` / `log_handoff`）只保留接口签名定义并标注 T2，本周不实现上报链路、不在演示中使用；
3. **接入与标准化：** 接收 OTLP/契约格式 Trace（实时入库或文件导入），标准化写入 spans 与事件表；断链和字段缺失按 docs/06 降级处理而不是崩溃；
4. **因果图构建（T1 口径）：** 由 parent_span_id 层级、步骤时序与数据流启发式（上游步骤的输出内容出现在下游步骤的输入中）构建有向图，启发式边携带置信标记；state/handoff 边只保留数据模型定义（T2），本周不构建；提供按 trace_id 查询因果路径的能力；
5. **规则/不变量引擎（T1 规则集）：** 至少实现 3 类确定性规则（工具参数 Schema 违例、步骤输出契约违例——格式错误/必填字段缺失、异常与超时传播），每条命中生成带证据引用的候选；规则以声明式配置（YAML/JSON）+ 引擎代码分离；另实现**成功/失败 Diff 候选生成器**：与最近成功基线逐步骤对比参数与输出结构，首个显著分歧点生成「Diff 分歧」候选——静默质量故障主要靠它定位首故障点；
6. **轨迹评估模型接口 + 双实现：** 定义 `Evaluator` 接口（输入因果图+事件，输出候选+反证）；默认 Mock 实现基于启发式产出至少 1 个「模型推断」级候选和 1 条反证，模拟异步延迟与超时失败路径；可选 `ClaudeCodeEvaluator` 实现，子进程调用 `claude -p --output-format json` 做真实语义诊断，输出强制走同一结构化证据校验；
7. **诊断聚合：** 合并规则与模型候选、按证据权重排序、Top-3 截断、证据等级映射；无证据候选丢弃；
8. **复核与资产：** 复核提交（三态必选、If-Match 冲突返回 409）、confirmed 事故一键转回归用例（打包输入引用+不变量）、门禁运行（对回归集重放规则校验，输出 pass/warn/block 报告）；
9. **前端工作台：** 覆盖运行记录、事故列表、诊断工作台（含证据卡片与 Diff）、复核、回归与门禁五个主页面；遵循本仓库 `.claude/rules/web/standards.md`（React + TS、Props 接口、API 层 + hooks 封装、禁止组件内直连 API）；诊断区按「规则结果先渲染、模型结果增量出现」的时序呈现。

前端若时间受限，允许把 Diff 视图降级为字段级表格对比，但主流程五页不得缺页。

### 任务 5：可运行 Demo

对应原始任务：「跑通端到端最小可用 Demo」。

Demo 的主路径必须是**真实数据现场计算**，不允许「播放预置结果」：

- **真实态演示（主路径）：** `demo` 命令启动全栈后，`demo-run` 现场执行示例 Agent——至少一次正常、两次不同注入，其中必须包含静默质量故障（全程无报错、由校验检出，现场展示「报错步骤不等于根因步骤」乃至「无报错也能定位」）；Trace 经接入层实时入库，事故、诊断候选、证据全部由后端现场计算生成，演示者在前端完成「打开事故 → 复核确认 → 转用例 → 门禁」闭环（对应第二周「三步闭环」承诺，主操作 ≤ 3 次）；
- **离线态验证（CI/评分兜底）：** 无网环境下 `demo-offline` 用录制 fixtures + Mock 评估器跑通同一条流程；E2E 冒烟测试（Playwright 或 API 级脚本）基于此态自动走通主流程，作为「Demo 可运行」的机器证据；
- **诚实性硬规则：** 代码库中禁止出现预写的诊断候选、证据文案或复核结论；评分者改动故障注入参数应能观察到诊断结果随之变化；每处故障注入点在 DEMO.md 中如实标注；
