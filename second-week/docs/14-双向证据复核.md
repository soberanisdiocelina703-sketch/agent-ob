# 任务 14：设计增强——双向证据复核

这项设计以主流诊断产品的详情页与确认流程为基础，做一处克制增强：**支持证据与反面证据同屏呈现，并且都能回到原始记录核对。**

**解决的问题：**

1. AI 结论可能表达流畅但证据不足；
2. 用户看到未经校准的精确分值后容易直接确认，忽略反例；
3. 单一「确认」按钮产生的反馈信息量太低，难以用于后续校准。

**设计方式：**

- **支持证据：** 展示能解释候选原因的事实、传播链和成功/失败对比，每一项必须附原始事件引用；
- **反面证据与其他解释：** 独立检索可能推翻该原因的事实及替代解释；未找到有效内容时如实说明，不把「没有反证」包装成确定结论；
- **复核结论：** 固定使用三个清晰动作——「确认是根因」「排除该原因」「暂需补充证据」。排除时选择理由，证据不足时生成待补数据清单；
- **历史案例与校准：** 每次复核进入校准日志；已确认事故进入历史案例库，后续相似诊断可引用，但历史案例只作为辅助信号；
- **信息层级：** 对外展示证据等级，内部原始分数不直接展示；原始证据和差异对比优先；证据不足的候选降级为线索，不进入正式复核流程。

**为什么这属于克制的增强：** 页面仍然是工程产品常见的「详情信息 + 双栏对比 + 底部操作」结构，用户不需要理解新的角色、剧情或术语。变化只发生在证据组织和反馈质量上，直接服务于减少误判。

**用户如何使用：** 从诊断工作台打开候选原因 → 核对支持证据、反面证据与其他解释 → 必要时跳回原始事件或 Diff → 提交复核结论。全程一屏完成，预计 30 秒到 2 分钟。

**复核示例（FM-07 主线案例，证据全文见 [00-故障分类与案例事实源.md](00-故障分类与案例事实源.md) 0.3 节）：** 事故 `INC-2026-0821-017`，候选 1「索引重建导致检索排序漂移，已废止政策 v3 挤占 top-1，现行政策 v5 被 top_k 截断」。

| 支持证据（4 条） | 反面证据（2 条） |
|---|---|
| E1 检索结果集 Diff：失败链 top-3 为 v3(0.83)/general_v2(0.81)/shipping_v4(0.80)，基线 top-1 为 v5(0.86)；v5 在失败链中排第 4 被 top_k=3 截断 | C1 同期 23 条链同样召回 v3 但答复正确（16 例非定制商品、7 例模型选用 top-2）→ 根因是复合条件：「排序漂移」+「模型不校验 effective_date」，不变量须同时约束检索层和模型层 |
| E2 政策文档版本 Diff：v3 §2.1「7 天无理由退款」已废止，v5 §2.1「定制类不支持无理由退款」现行 | C2 重建前 30 天该 query 的 top-1 稳定为 v5（采样 412 次无例外）→ 排除「query 表述歧义」这一替代解释 |
| E3 索引重建事件：2026-08-20 22:10 embedding v2→v3 覆盖 12,847 文档，事故首现滞后 1h37m | |
| E4 模型采信链：S5 上下文仅含 v3 条款，S8 输出与 v3 §2.1 逐字一致 | |

这个示例说明双向证据的价值：C1 不是「削弱结论的噪音」，它把结论从「漂移导致失败」修正为「漂移 + 模型不校验生效日期的复合条件」，直接改变了不变量的写法和修复范围；C2 则排除了一个貌似合理的替代解释。只看支持证据得不到这两个结论。

**原型落地：** 「诊断复核」页已实现两栏证据、原始事件回跳和三个复核动作；确认根因后以标准成功状态提示并引导生成回归用例；排除原因时弹出理由选择；证据不足时生成待补数据清单。

**价值闭环：** 同屏展示反面信息降低轻信，结构化理由提高校准数据质量，已确认结论再转回归用例，避免把错误判断固化进发布门禁。

## 14.1 证据数据契约

| 字段 | 要求 | 用途 |
|---|---|---|
| `side` | `support` 或 `counter` | 区分支持与反面证据 |
| `kind` | 状态 Diff、传参、工具参数、记忆读取、基线 Diff 等 | 说明证据类型 |
| `span_ref` / `event_ref` | 至少一个可解析 | 回到原始事实 |
| `excerpt` | 只保留必要摘要，敏感内容已脱敏 | 首屏快速阅读 |
| `weight` | 内部排序使用，不直接对外展示 | 证据聚合 |
| `calibration_version` | 候选等级映射版本 | 复盘等级变化 |

证据卡不是模型自由文本容器。引用对象不存在、项目不匹配或已被权限策略拦截时，该证据不能参与“证据充分”的判断。

## 14.2 复核状态机

```text
待复核
├─ 确认是根因 → 可生成回归用例
├─ 排除该原因 → 记录结构化理由，可指向正确原因
└─ 暂需补充证据 → 生成待补数据清单，补齐后重新诊断

任一结果 → 重新复核 → 保留旧记录并用 superseded_by 串联
```

并发提交使用版本号控制。第二名复核人提交旧版本时，界面展示现有结论，允许附议或发起重新复核，不静默覆盖。

## 14.3 异常处理

- 没有反面证据：显示“未找到有效反证”，不能用空白暗示结论确定；
- 支持与反面证据冲突：冲突项置顶，证据等级不得为“证据充分”；
- 引用失效：标记失效并禁止提交确认；
- 权限不足：允许查看已脱敏证据，但隐藏复核操作；
- 数据不完整：生成待补字段和事件清单，保留当前诊断版本；
- 重新复核：由原结论生成的回归用例进入待复核状态。

## 14.4 是否有效的判断

这项设计的效果不能只看复核按钮点击量。至少要同时观察：反面证据被展开的比例、用户回跳原始事件的比例、排除理由的完整度、重新复核率，以及不同证据等级对应的实际确认率。只有用户确实核对证据且等级能被校准，双向证据才算降低误判，而不是增加一栏文字。

补充一条口径修正的动机（结果记录在 00 事实源 0.7 节）：确认率与命中率必须按故障类型分桶统计——规则可判定类（FM-02/03/04）、混合类（FM-01/05/06）、语义复合类（FM-07/08/09）的诊断难度差异是数量级的，合并成单一数字会让规则类的高确认率掩盖语义类的真实表现，等级校准也会因此失真。
