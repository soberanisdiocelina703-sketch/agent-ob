# 任务 3：产品方案说明

### 3.1 为什么（谁在痛，代价是什么）

依据第一周 4.2 节，运行单 Agent 系统的团队（AI 平台负责人、Agent Owner、SRE）面临一个具体困境：**症状步骤不是根因步骤，更难的是链路可能根本不报错**。以主线案例 FM-07 检索排序漂移（事故 `INC-2026-0821-017`，完整事实见 [00-故障分类与案例事实源.md](00-故障分类与案例事实源.md) 0.3 节）为例：向量库索引重建后 embedding 模型升级，已废止的退款政策 v3 挤占检索 top-1，现行政策 v5 被 `top_k=3` 截断、从未进入模型上下文。链路上没有任何错误信号——9 步全部 success、HTTP 全 200、检索非空、输出格式合法，规则引擎判定「无异常」——但 Agent 按已废止政策答复用户，24 小时影响 37 个会话、14 例投诉。真实根因在 S4 检索步骤，比症状步骤 S8 早 4 步，只有把失败链与成功基线的检索结果集做跨步骤比对才能看出。现有工具（含 AgentLoop）能把几百个 Span 完整展示出来——树、图、时序、轨迹五种视图——但这类比对仍然要人翻着看。

**为什么选「无低成本解法」的类别做价值论证：** 第二周版本以 FM-01 状态过期为主线案例，方案自查（[R02](../research/R02-方案自查走查记录.md)）发现它有结构性弱点——存在成本极低的解法（快照加 TTL + 变更订阅），撑不起「必须靠因果图 + 证据化诊断」的价值主张，自查时给它的定性是「照着答案写原因」。复盘确认这是案例选择问题而非方案问题：因果定位机制对所有故障类型同构，但价值论证必须选没有一行配置能解决的类别。九类中只有 FM-07/08/09 满足「无低成本解法」——执行层全成功、根因是复合条件、证据必须跨步骤比对——因此本版本把价值论证与演示主线切换到这三类，FM-01 降级为普通事故保留。分类口径与切换决策见 00 事实源与设计决策 D-09。注意：FM-07/08/09 的诊断能力属 T2 设计中，尚未实现。

代价可量化：排障工时（一次跨步骤事故平均需要资深工程师半天到两天；FM-09 这类无症状步骤的事故要等财务对账才暴露）、事故影响时间（MTTR，平均修复时长）、同类问题复发（经验沉在个人聊天记录里，换个人接手重新踩坑）。

### 3.2 解决什么问题

**场景定义（一句话，承接第一周 4.7 节格式）：**

> 为【运行单 Agent 生产系统的平台团队与 SRE】在【生产事故排查】情境下解决【症状步骤不等于根因步骤（甚至全链无报错）、证据散落难以定位】的问题，通过【首故障点定位 + 证据化诊断 + 成功/失败 Diff + 复核闭环】实现【MTTR 下降、同类问题不复发、修复可验证】。

**三个待验证的目标指标（均为产品目标，不是本期实测结果）：**

1. 首故障点 Top-3 命中率 ≥ 70%（用已知根因事故集实测）；
2. 证据接受率 ≥ 60%（用户确认是根因的比例）；
3. 从打开事故到生成回归用例 ≤ 3 次主操作、≤ 10 分钟。

### 3.3 怎么解决（五层机制，讲给不懂技术的人）

1. **数据层——先把过程记全。** 通过标准探针（OTel，开放遥测）记录 Agent 每一步做了什么：调了哪个模型、用了哪个工具、读写了什么状态和记忆、把什么传给了下一步。就像给整条执行流水线装监控摄像头。
2. **因果层——把「先后」变成「因果」。** 系统把这些记录连成一张因果图：哪一步写的状态被哪一步读了、上一步的输出成了下一步的输入。摄像头拍的是画面，因果图画的是「哪一步碰了哪一步」。
3. **证据层——先用规则抓现行，再用模型断疑案。** 格式错了、字段丢了、状态过期了——这类确定性问题用规则直接判定，铁证如山；「答案看着对但业务上错了」这类语义问题（如检索排序漂移、多轮上下文冲突、重试状态放大）才交给模型分析，且模型必须指出具体证据，说不出证据的结论不许上屏。
4. **复核层——系统给证据，人做确认。** 系统把「根因成立的理由」和「不成立的反证」摆在一起（诊断复核），由工程师复核。每次确认及其理由都被记录，系统越用越准。
5. **资产层——已确认的问题沉淀为防线。** 每个确认根因的事故一键变成回归用例，下次发版前自动重跑，同样的坑不踩第二次。

### 3.4 使用者与职责边界

| 使用者 | 进入产品时要完成的事 | 产品提供 | 产品不替代 |
|---|---|---|---|
| Agent 开发者 | 找到最早异常步骤，核对输入、状态和工具参数 | 候选原因、因果路径、原始事件引用 | 代码修复和上线决策 |
| SRE / 值班人员 | 判断影响范围和处理优先级 | 失败模式簇、影响会话、趋势和复核状态 | 告警平台与事故指挥系统 |
| 测试 / 发布人员 | 把已确认问题变成发布前检查 | 回归用例、不变量和门禁报告 | 完整 CI/CD 平台 |
| 平台管理员 | 保证采集、权限和隐私策略可用 | 接入体检、角色、脱敏和告警配置 | 通用 APM 与身份系统 |

### 3.5 使用前后变化

没有寻迹时，排障从错误日志开始，工程师按时间翻 Span、猜测上游状态，再手工找一条成功链对照。问题修复后，原因通常留在聊天记录里。使用寻迹后，入口仍是熟悉的运行记录和事故列表，但事故详情先给首故障点和证据；确认后，输入、上下文和不变量直接进入回归集。变化不是增加一个“智能结论”，而是减少查找、搬字段和重复验证。

### 3.6 指标定义

| 指标 | 分子 / 分母 | 数据来源 | 何时统计 |
|---|---|---|---|
| Top-3 命中率 | 已知根因位于前三候选的事故数 / 已知根因事故总数 | 标注事故集、诊断结果 | 每个规则包或模型版本发布前 |
| 证据接受率 | 复核为“确认是根因”的候选数 / 进入正式复核的候选数 | `verdicts` | 按周、按来源分桶 |
| 处置时间 | 打开事故至生成回归用例的耗时 | 前端事件、回归用例创建时间 | 正式用户测试和线上使用阶段 |
| 同类复发率 | 已关闭模式在观察窗内再次触发的次数 | 失败模式簇、事故状态 | 按月 |

目标值用于设定验证门槛，不写成已经取得的业务结果。若 Top-3 命中率低于 70%，诊断入口保留但不得对外宣传命中效果；若证据引用完整性低于 100%，对应候选直接不上屏。
