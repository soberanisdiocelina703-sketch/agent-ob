# 任务 0：故障分类与案例事实源

本文件是**唯一事实源**。所有文档、原型和演示稿中的故障类型编号、案例 ID、证据内容和不变量都以此为准；任何一处改动必须先改本文件。设立本文件的原因见 [12-设计决策](12-设计决策.md) D-09。

## 0.1 为什么重排分类

第二周原始分类有六类，主线演示案例为 FM-01「状态与记忆过期」。中期评审指出该案例存在**结构性弱点**：它有一个成本极低的解法（给快照加 TTL 与变更订阅），因此撑不起「必须靠因果图 + 证据化诊断」的价值主张——评审原话是「照着答案写原因」。

复盘后确认这是**案例选择问题，不是方案问题**：因果定位机制对所有故障类型同构，但演示案例必须选那些**没有一行配置能解决**的类别。因此新增 FM-07/08/09 三类，主线演示切换为 FM-07；FM-01 降级为列表中的普通事故，仍然保留（它是真实存在的故障类型，只是不适合当主线）。

「有无低成本解法」是本期新增的评估维度：**只有「无」的那三类才能证明诊断产品的必要性**，前六类中的多数可以靠工程规范预防。产品对全部九类提供诊断，但价值论证和演示主线只用 FM-07/08/09。

三类新故障的共同结构特征，也是它们无法被配置解决的原因：

1. **执行层全部成功**——所有步骤 `execution_status=success`，HTTP 全部 200，无异常无超时，规则引擎判不出任何问题；
2. **故障由业务侧发现**——用户投诉、Judge 低分或财务对账，而不是告警；
3. **根因是复合条件**——单一条件不必然导致失败，需要两个条件同时成立（见各案例反证 C1）；
4. **证据必须跨步骤比对**——单看任何一个 Span 都正常，只有把上游步骤的输出与成功基线对照才能看出差异。

| 症状步骤 | **无报错点**——本例连症状步骤都需要靠外部对账反推 |
| 首故障步骤 | **S6 `TOOL` refund_api 首次调用超时**（真实根因） |
| 证据等级 | 证据充分 |
| 影响面 | 6 个会话 / 24h，涉及金额 ¥1,080 重复退款 |

### 故障叙述

同一笔订单被退款两次，¥180 × 2 = ¥360。链路显示「执行成功」，因为从 Agent 视角看确实成功了：首次调用超时，自动重试，第二次成功。**财务日终对账才发现重复**——这是三个案例中最难的一类，它没有任何症状步骤可供定位，链路上找不到任何异常标记。

### 根因机制

S6 首次调用 `refund_api` 客户端 30s 超时，但**服务端实际已完成退款**（超时发生在响应返回途中）。框架按 `retry_on=[timeout]` 策略自动重试，S8 第二次调用返回 200。两次请求的 `request_id` 不同（`req-a1f2` / `req-b7c3`），而 `refund_api` **不支持幂等键**，因此服务端记录了两笔独立的退款交易。

超时重试本身是正确的容错设计。问题在于：**对非幂等的写操作重试**。

### 支持证据（4 条）

| 编号 | 类型 | 来源 | 内容 |
|---|---|---|---|
| E1 | 两次调用记录 | 规则判定 | S6 `refund_api` `request_id=req-a1f2`，client timeout 30.0s（无响应体）；S8 `refund_api` `request_id=req-b7c3`，HTTP 200，`refund_id=RF-77219` |
| E2 | 服务端双记录 | 规则判定 | `refund_txn` 表两条记录：`txn-9981`（06:12:03，¥180，req-a1f2，状态 SUCCESS）与 `txn-9987`（06:12:36，¥180，req-b7c3，状态 SUCCESS）——证明首次调用服务端已成功 |
| E3 | 入参无幂等键 | 规则判定 | 两次请求体均无 `idempotency_key` 字段；`refund_api` OpenAPI 契约中该字段不存在 |
| E4 | 重试策略配置 | 规则判定 | framework retry policy：`max_attempts=2`，`retry_on=[timeout]`，未声明 `require_idempotent=true`；工具注册表中 `refund_api` 未标注 `idempotent` 属性 |

### 反面证据（2 条）

| 编号 | 内容 | 对结论的影响 |
|---|---|---|
| C1 | 超时重试是正确的容错设计，关闭重试会导致大量本可自愈的瞬时失败暴露给用户（近 7 天有 47 次重试后成功） | **根因是复合条件**：「超时重试」+「接口无幂等」。修复方向是补幂等键而非禁用重试，这直接决定不变量的写法 |
| C2 | 同期 8 条超时重试链未产生重复副作用——那些调用的是 `order_api`（只读）与 `risk_check`（幂等） | 确认根因边界：只有「非幂等写操作 + 重试」的组合才危险，不变量应按工具属性而非全局约束 |

| 排名 | 候选 | 来源 | 证据等级 | 首故障点 |
