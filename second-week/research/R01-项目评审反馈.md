# 项目评审反馈记录

记录日期：2026-08-19  
评审对象：第二周产品文档、总览页与交互原型  
评审人：R01（项目提交人，匿名记录）  
记录方式：逐轮查看交付物后提出问题，修改完成后做文件与代码核验

这份记录只收录实际收到的反馈。未发生的任务耗时、完成率和受测者原话不写入结果。

## 原始反馈与处理

| 编号 | 原始反馈摘录 | 识别出的问题 | 处理结果 | 核验 |
|---|---|---|---|---|
| F-01 | “我不太喜欢根因庭审，法官裁决这种说法” | 角色隐喻增加理解成本，也不符合工程工具语气 | 全部改为“诊断复核、确认是根因、排除该原因、暂需补充证据” | 全项目检索旧术语，无残留 |
| F-02 | “产品名 ai 味太重了，换一个更自然的”“原型先保持主流产品的一贯风格” | 名称与视觉表现过度追求概念感 | 产品名改为“寻迹”；界面回到浅灰背景、白色卡片、左侧导航和标准蓝主操作 | 原型 CSS token 与页面标题核验 |
| F-03 | “当前项目是不是只有异常才有数据，正常 trace 会有显示吗” | 运行入口只强调事故，容易形成“正常运行不可见”的误解 | 增加运行记录和正常 Trace 详情；执行状态、质量结论、事故状态分开 | 运行记录现有成功、失败、质量未评估三类记录 |
| F-04 | “步骤分类不对吧……这分类是通用的吗” | 把退款业务节点混入平台通用分类 | 拆分 `raw_step_type`、归一化 `step_type`、`step_name` 与 `failure_type` | 文档字段、筛选器和 6 类事故记录对照 |
| F-05 | “哪来的两个原型” | 总览和交互原型的角色没有说清 | 明确只有一份交互原型；总览只是提交入口 | 评分索引与任务 7 均使用同一口径 |
| F-06 | “讲方案摘要里的图片放到核心流程设计这一节里” | 图片位置打断摘要阅读 | 流程图移动到核心流程章节，技术图放在技术方案章节 | 总览页相对图片链接核验 |
| F-07 | “运行记录，事故列表，回归集的每一条数据右半边界面是空白的” | 通用 CSS 把表格设为 `display:block`，行内容按固有宽度收缩 | 恢复标准 table 布局；三个列表容器仅在窄屏横向滚动 | 3 个 `data-table-card`；无 block table 规则；HTML/JS 校验通过 |
| F-08 | “做成一个项目目录结构……作为一个给大模型去评分的索引文件” | 交付物缺少评分入口，单体长文不利于逐项核验 | 新增评分索引首页、14 个独立任务文档、UI 规范和证据目录 | 链接检查与任务覆盖检查 |

## 本轮可以下的结论

- 评审人能明确指出术语、信息架构、数据口径和布局问题，反馈已经逐项落到文件或代码修改。
- 运行记录不再只展示异常；技术成功与业务质量通过不再混为一谈。
- 原型的主导航、表格宽度和分类口径经过真实反馈迭代。
- 这轮记录不能替代正式的多人任务测试，因此不计算完成率、平均耗时或用户满意度。
