# 中期评审反馈记录

记录日期：2026-08-24  
评审对象：第二周产品方案（候选场景定义、主线演示案例、故障分类口径）  
评审人：项目负责人  
记录方式：评审人对方案提出质疑，双方逐条对质后形成结论，处理动作完成后回填状态

这份记录如实收录双方观点，包括我方承认的部分、我方不接受的部分和最终仍存的分歧。不写成单方面认错，也不写成单方面辩护。

## 质疑一：「跨 Agent」概念不清

### 评审人观点

候选场景里的"跨 Agent 因果故障定位"没有说明"跨 Agent"指什么：是"一个主 Agent 带多个子 Agent"，还是"多个独立 Agent"？Agent 以什么形式存在、彼此怎么通信，方案里都没有交代。概念边界不清，后续的数据模型和诊断逻辑就没有落点。

### 我方回应

承认定义缺失，当场补齐口径：

- **两种拓扑都算**。关键特征不是拓扑形状，而是"报错的执行体与产生根因的执行体不是同一个"。主从结构、对等结构都会出现这个特征。
- **存在形式三种**：同进程内的框架节点（LangGraph 节点、Agent SDK 子代理）；独立部署的 Agent 服务；混合形态——远程 Agent 经 MCP 或 A2A 协议被当作一个"工具"调用，调用方甚至不知道对面是个 Agent。
- **通信四条通道**：交接（Handoff）、同步调用、异步消息、共享状态与记忆。其中共享记忆最隐蔽——A 写入、B 读取，调用树上看不出任何依赖关系，必须建因果读写边（谁写了这个键、谁后来读了它）才能发现。

### 达成的共识

上述定义作为"跨 Agent"的统一口径写入事实源文档，候选场景描述同步更新。此项无分歧。

## 质疑二：主线案例「状态与记忆过期」是"照着答案写原因"

### 评审人观点

这是本轮最严重的质疑。FM-01（状态与记忆过期）看起来不是从真实需求里长出来的，而是先有了"要演示因果诊断"这个答案，再倒推出一个方便画图的故障：

1. 该案例有成本极低的解法——给快照加 TTL、订阅变更事件。一行配置能解决的问题，撑不起一个诊断产品的价值主张。
2. 成熟 Agent 系统已在每层部署了同类防线。以 Claude Code 为例：写前校验 live 状态（Edit 的 old_string 匹配失败即拒绝）、文件变更通知、上下文里显式标注快照时效。防线密到这类故障很难发生。

### 我方回应

**承认的部分**：案例选择确实是演示便利性驱动，不是需求强度驱动，这一点站不住。六类故障里"状态过期"是最容易画图讲清、但最不能代表产品价值的一类。主线案例必须换。

**不成立的部分**（我方坚持，逐条陈述）：

- (a) **类别错误**。Claude Code 的防线是 Anthropic 为编码场景手写进 harness 的，不是 Agent 运行时的通用能力。用 Agent SDK 自建业务 Agent 时，记忆层、新鲜度校验全要自己实现。"用 Claude Code 做订单助手就不会有这问题"混淆了两类东西——Claude Code 是成品应用，不是构建业务 Agent 的运行时。
- (b) **防线迁移不过去，因为真值源性质不同**。文件在本地、读取免费、读完即最新，所以"写前重读一次"成本为零；订单状态在远端，有延迟、限流和调用费用，"每次查 live"在业务场景是要付账的，团队必然做快照缓存，过期窗口必然存在。
- (c) **即使装齐防线，故障只是换了形态**。Claude Code 的 Edit 拒绝本身也是一次失败：它告诉你 old_string 没匹配上，但不会告诉你"40 轮前读的文件在此期间被别的进程改过"。防线把静默错误变成显式报错，归因这一步依然要人往回翻。

**双方都接受的事实**（不依赖任何特定故障类型成立）：Agent 是多步骤的，报错步骤与根因步骤经常不是同一个；现有工具（Langfuse、LangSmith 一类）只能把几百个 Span 摊开给人看。产品价值锚在这句话上，而不是锚在某一类故障上。

### 达成的共识

- 主线演示案例从 FM-01 切换到无低成本解法的故障类型；FM-01 降级为普通事故保留，不再承担价值论证。
- 新增故障类型的筛选标准：执行层全成功（HTTP 全 200，规则引擎判不出异常）、故障由业务侧发现（用户投诉 / Judge 评分 / 对账）、根因是复合条件、证据必须跨步骤比对才能成立。满足这四条的故障，"加一行配置"解决不了，人工排查也没有捷径，才是诊断产品该吃的场景。

### 仍有分歧的部分

对"Claude Code 式防线能否证明该类故障不值得诊断"，双方没有达成一致：评审人认为防线的存在至少说明头部团队会自行消化这类问题；我方认为防线只覆盖编码场景且只改变故障形态（见上文 a/b/c）。此分歧不影响处理动作——主线案例切换后，该争论不再影响产品主张，故搁置，留待第一周记录的 AgentLoop 等编码 Agent 审计类产品的市场表现提供旁证。

## 处理动作（已完成）

1. 新增三类"无低成本解法"的故障类型：
   - **FM-07 检索排序漂移**：检索全部成功，但排序权重被上游配置变更悄悄改掉，答案质量下滑由 Judge 与投诉发现。
   - **FM-08 多轮上下文冲突**：多轮对话中先后注入的两段上下文互相矛盾，模型采信了错的那段，单步看每一步都合理。
   - **FM-09 重试状态放大**：重试成功掩盖了首次执行留下的副作用，副作用被后续步骤消费并放大。
   - 三类共同结构：执行层全成功、业务侧发现、复合条件根因、证据跨步骤比对。
2. 主线演示案例切换为 FM-07（事故 INC-2026-0821-017）；FM-01 降为普通事故保留在事故列表中。
3. 建立唯一事实源 `docs/00-故障分类与案例事实源.md`，所有文档与原型的故障分类、事故编号、案例细节统一以此为准，消除多处口径漂移的可能。
4. 目标 Agent 定位写清：不是编码 Agent，而是用 LangGraph / Dify / Coze / Agent SDK 搭建的生产业务 Agent（客服、工单、财务审批、数据分析），运维方是平台团队与 SRE，规模前提是每天几千到几十万次执行。编码 Agent（Claude Code / Cursor / Codex）是潜在数据源而非竞品——第一周报告已记录 AgentLoop 在做这类行为审计。

## 本轮可以下的结论

- 评审人的两个质疑一个指向概念严谨性，一个指向价值主张的根基，均属方案级问题而非表述问题。
- 质疑二迫使案例筛选标准从"好画图"换成"无低成本解法 + 执行层全成功 + 业务侧发现"，这是本轮最大的方案改进。
- 承认与反驳同时存在是正常评审结果；把不成立的反驳也如实写下，是为了下次评审可以继续对质，而不是每轮从零开始。
