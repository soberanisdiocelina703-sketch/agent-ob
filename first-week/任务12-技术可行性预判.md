# 任务 12｜技术可行性预判：实现难点与第 2/3 周路径

## 1. 预判结论

选择“长耗时 Agent 请求瓶颈定位”作为首场景，技术上可在第 2 周形成可演示闭环，第 3 周形成可验证的差异化原型。

最难的不是画瀑布图，而是保证时间/关系数据可信，并正确处理异步、多 Agent、并行、流式输出和采集缺失。

## 2. 必要数据

### 最小字段

- `trace_id`、`span_id`、`parent_span_id`。
- Span Link（异步/跨 Trace）。
- `start_time`、`end_time`、`status`。
- Span type：Agent、LLM、Tool、Retriever、MCP、Chain 等。
- Agent/应用/版本/环境/Session/User 标识。
- 模型名、Token、工具名、错误码。

### 性能解释增强字段

- request、queue、first_token、last_token 时间。
- 重试次数和 backoff 事件。
- 客户端与服务端 Span。
- 输入规模、输出规模。
- 资源属性：服务、主机、Pod、Region。

## 3. 核心算法

### 关键路径

1. 按父子和 Link 构建有向图。
2. 校验时间区间、环和时钟偏差。
3. 合并同步调用和异步等待关系。
4. 计算从根开始到用户完成的最长墙钟路径。
5. 计算节点边际贡献，不简单相加并行 duration。

### 等待分类

规则优先：

- LLM request → first token：模型排队/首包等待。
- Tool client → server：网络与服务端执行。
- 同操作重复 + 错误：重试。
- 重试间隔递增：退避。
- 同层步骤无重叠且无依赖：潜在串行化。
- 父 Span 活跃但无子事件：本地计算、等待或采集缺失候选。

### 正常基线

先按结构化条件匹配，再考虑语义 embedding：

```text
同 Agent + 同 Trace 名/意图 + 同版本/环境
+ 相似工具集合 + 相似输入 Token
+ 成功状态 + 正常耗时分位
```

必须展示匹配条件，避免“黑盒基线”。

## 4. 主要技术难点

| 难点 | 风险 | 处理路径 |
|---|---|---|
| 异步/消息队列 | 父子关系无法表达因果 | 使用 Span Link；区分调度与执行 |
| 多 Agent 委派 | 跨 Trace 或跨服务断链 | 传播 Trace Context；保存委派 Link |
| 循环与重试 | 图重复、难以聚合 | operation key + attempt 编号 |
| 流式输出 | duration 无法表达用户感知 | 记录 first/last token 事件 |
| 时钟偏差 | 时间线错位、负耗时 | Collector 校时、偏差估计和告警 |
| 自动探针兼容 | 框架升级导致漏采 | 版本矩阵、契约测试、采集健康度 |
| 大输入输出 | 存储和 UI 性能 | 对象存储、摘要、按需加载、截断标识 |
| 敏感数据 | 合规与泄露 | 采集端脱敏、RBAC、保留期、审计 |
| AI 误因果 | 错误建议 | 确定性证据先行、候选而非绝对结论 |

## 5. 推荐架构

```text
Agent / Framework / Runtime
  │ OTel SDK / 自动探针 / Hook / eBPF补充
  ▼
Collector / Gateway
  ├─ 字段校验与映射
  ├─ 采样、批处理、脱敏
  ├─ 断链/时钟检测
  ▼
Event Queue → Trace Processor
                ├─ 关系重建
                ├─ 关键路径
                ├─ 等待/重试分类
                └─ 基线匹配
  ├─ 列式事件库
  ├─ 对象存储
  ├─ 元数据库
  └─ 现有日志/指标系统
  ▼
Diagnosis API → UI / Alert / AI Copilot / Eval
```

## 6. 第 2 周路径：可演示闭环

### 目标

对三类预设慢请求，用户能在单页看到正确瓶颈和证据。

### 工作项

1. 选择 LangChain/LangGraph 或自研示例 Agent。
2. 用 OTel/框架探针采集 Agent、LLM、Tool、Retriever Span。
3. 先用 JSON/轻量数据库，不建设大规模存储。
4. 实现 Trace 列表和关键路径时间线。
5. 实现 Span 输入输出、错误、Token、资源属性。
6. 实现采集健康检查：断链、字段缺失、时间不守恒。
7. 构造：慢工具、模型重试、上下文膨胀三类故障。
8. 用规则生成诊断卡；AI 只做摘要。

### 验收

- 三类故障均能被规则正确识别。
- 关键路径与人工计算一致。
- 不完整 Trace 会提示风险而非给确定根因。

## 7. 第 3 周路径：差异化验证

### 目标

证明关键路径、基线对比和证据化 AI 比普通 Trace 浏览更快。

### 工作项

1. 增加正常/异常 Trace 自动匹配与差异视图。
2. 增加等待类型和关键路径贡献率。
3. 联动日志或资源指标中的至少一种。
4. 增加 AI 根因候选，固定输出证据/反证/置信度。
5. 建立 20–30 条专家标注 Trace。
6. 与 Langfuse 或云厂商控制台做同题定位对比。

### 验收

- Top-1 瓶颈识别准确率 ≥ 80%。
- 目标用户 60 秒内完成定位。
- 比基线产品减少点击数或定位时间至少 30%。
- AI 误导率有独立统计。

## 8. Build / Buy 边界

### 复用/采购

- OTel SDK/Collector。
- 通用日志、指标、告警。
- 对象存储和列式数据库。
- 框架已有 Instrumentation。

### 自主构建

- Agent 关键路径和等待语义。
- 正常基线匹配。
- 采集健康度。
- 用户等待与工程时间对齐。
- 证据化 AI 诊断和反馈评测。

### 暂不构建

- 全套 Prompt 管理。
- 完整离线评测平台。
- 通用日志搜索产品。
- 一开始就追求超大规模多租户架构。

## 9. Go / No-Go 技术门槛

### Go

- 目标框架的父子、Tool、LLM、first token 数据覆盖率 ≥ 90%。
- 关键路径对测试样本计算正确。
- 采集开销在目标范围内。
- 脱敏后仍保留足够诊断信息。

### No-Go / 调整

- 关键框架无法稳定传播 Trace Context。
- 大量关键等待无法通过任何事件或指标观测。
- 合规要求禁止采集所有可用于诊断的上下文。
- 自动探针开销或兼容成本超过首期收益。
