# 任务 05｜设计逻辑推演：竞品为什么这样设计

## 1. 分析框架

从“用户角色、问题结构、数据结构、商业底座”四个维度反推设计，而不是只评论页面样式。

## 2. 阿里云：为什么提供五种 Trace 视图

### 原因一：一个 Trace 同时存在五类认知问题

- 调用树回答层级。
- 链路图回答依赖和聚合拓扑。
- 时序线回答时间分布。
- 推理轨迹回答语义过程。
- 链路分析回答指标汇总。

因此多视图并非单纯视觉冗余，而是不同排障任务的映射。

### 原因二：目标用户跨开发与运维

Agent 开发者关心 Prompt、Tool、输入输出；SRE 关心服务、实例、日志、资源和告警。阿里把 Agent 语义视图和传统 APM 视图放在同一 Trace 下，服务两类用户。

### 原因三：依托已有云可观测底座

ARMS、SLS、微服务和云监控已经拥有 Trace、Log、Metric、事件和资源体系。AI Agent 可观测的设计自然采用“实体 → Trace → Span → 底层资源”的下钻方式，而不是另起独立平台。

### 设计代价

功能完整但认知成本高，新用户面对五种视图可能不知道从哪里开始。

## 3. 华为云：为什么强调 Session 和 Trace 回流

### 原因一：Agent 问题既是工程问题也是质量问题

单条 Trace 能解释一次执行，但用户体验发生在多轮 Session 中。华为用 Session 作为用户视角，再用 Trace 作为工程视角。

### 原因二：AgentArts 本身是开发与评测平台

生产 Trace 中的失败、低分或高价值案例，本身就是最真实的评测数据。因此设计了标注、筛选、回流数据集、在线评估和智能报告。

### 原因三：底层服务分工明确

Trace、Metric、Log 分别进入 APM、AOM、LTS。AgentArts 作为领域聚合层呈现统一体验。

### 设计代价

- 严格字段规范提高第三方接入门槛。
- 多底层产品导致计费、权限和数据一致性更复杂。
- 当前控制台调试/编排预览不上报运营运维，开发态与生产态存在割裂。

## 4. Langfuse：为什么转向 Observation-first

### 原因一：Agent Trace 越来越深、循环越来越多

传统“Trace 表 + Observation 子表”在超深 Agent 链路中查询和展示压力增加。Langfuse v4 将 Trace 表达为根 Observation，所有 Agent Step、LLM 和 Tool 都统一成事件行。

### 原因二：观测和评测共享数据原子

Score 可以挂在 Observation、Trace、Session 或 Dataset Run 上。统一事件模型使线上观测、人工标注、LLM Judge 和实验更容易连接。

### 原因三：开源产品需要中立和可扩展

OTel、开放 API、ClickHouse 和对象存储适合跨框架、大规模摄取与分析，也避免绑定单一云厂商。

### 设计代价

- v3 到 v4 带来 SDK/API 迁移成本。
- 自托管架构复杂。
- 缺少云厂商原生的基础设施根因联动。

## 5. 三家共同的设计规律

1. **对象层级趋同**：Session → Trace → Span/Observation → Event/Log。
2. **协议趋同**：OpenTelemetry 和 `gen_ai.*` 语义字段逐渐成为接入基础。
3. **路径趋同**：总览发现 → Trace 筛选 → Span 下钻 → 评测/告警/治理。
4. **差异来自底座**：云厂商强调底层资源联动，开源平台强调跨云和开放数据。
5. **AI 进入第二阶段**：先保证事实数据，再做根因总结、轨迹评估和自然语言操作。

## 6. 对我们设计的推演

### 应继承

- Session、Trace、Span、Event 的清晰层级。
- OTel 兼容和框架自动采集。
- 从 Trace 到日志/指标/评测的上下文保持。

### 应改变

- 不让用户先选择树、图或时间线，而是先选择问题：慢、错、贵、不准。
- 默认计算墙钟关键路径，而不是仅按 Span duration 排序。
- 自动匹配正常基线，减少人工筛选。
- 将采集完整度作为一等信息。
- AI 结论必须绑定证据、反证、置信度和反馈。

## 7. 结论

竞品的页面结构由其数据模型、目标角色和商业底座共同决定。我们的突破不在“少一张图或多一张图”，而在于把多视图背后的分析步骤自动化，让产品直接服务问题解决。
