## 一、核心结论（先看这里）

**首个产品场景应选：长耗时 Agent 请求的性能瓶颈定位。**

核心差距只有一句话：竞品帮用户"看见一条 Trace"，我们要帮用户"在 30 秒内用证据说清楚：时间花在哪、为什么慢、下一步该查什么"。

| 维度 | 竞品现状 | 我们的机会 |
|---|---|---|
| 定位速度 | 多视图手动阅读，中位 30 分钟 | 30 秒内自动定位关键路径 |
| 解释深度 | "这个 Span 花了 14 分钟" | "正常同类 1.8 秒，本次因 3 次 504 重试达到 14 分钟" |
| AI 可信度 | 无证据或仅总结 | 根因候选 + 支持证据 + 反证 + 置信度 + 下一步 |
| 采集可信度 | 缺失数据被当业务数据处理 | 采集健康度作为一等信息 |

## 二、竞品格局：三条路线，一个共同盲点

### 2.1 三家竞品定位

研究对象：阿里云 AgentLoop、华为云 AgentArts、Langfuse（三家覆盖国内主流云厂商 + 国际开源标杆）。

```
阿里云 AgentLoop    ——  云上全栈运维路线
  强项：Agent 语义 + 告警 + 底层资源联动（五种 Trace 视图、全局拓扑）
  弱项：视图多，依赖用户排障经验；采集方式较重

华为云 AgentArts    ——  观测到评测闭环路线
  强项：生产 Trace 一键回流评测集，Trace/标注/评测打通
  弱项：Trace/Metric/Log 分属 APM/AOM/LTS，三产品分别计费

Langfuse            ——  开放数据平台路线
  强项：MIT 开源、OTel 原生、跨模型跨框架、AI Engineering 全链路
  弱项：自托管包含 PG + ClickHouse + Redis + 对象存储，运维成本不低
```

### 2.2 三家共同点（也是我们的基线）

- 统一采用 Session → Trace → Span 三层结构
- 均兼容 OpenTelemetry + GenAI 语义属性（`gen_ai.*`）
- 排障入口相同：列表总览 → 筛选 → 下钻单 Trace
- AI 能力正从"总结"向"行动"演化（但可信度不足）

### 2.3 共同盲点（我们的切入点）

**三家都展示"发生了什么"，没有一家能直接回答"为什么用户等了这么久"。**

具体表现：
- 展示每个 Span 的耗时，但不计算真正影响端到端时间的**关键路径**
- 把采集缺失、时钟偏差当成正常数据处理（**数据可信度隐形**）
- AI 根因没有可验证的支撑证据（**结论不可信**）
- 无法自动调出同类成功请求作为基线对照（**诊断缺对比**）

## 三、场景选定：为什么是"长耗时定位"

### 3.1 五场景加权评分

| 场景 | 用户在问什么 | 加权分 |
|---|---|---:|
| **长耗时瓶颈定位** ★ | 时间到底花在哪一步 | **4.75** |
| 失败根因定位 | 为什么中断、谁的责任 | 4.45 |
| 错误输出复盘 | 是检索、Prompt 还是工具 | 4.25 |
| Token 成本治理 | 钱花在哪个 Agent | 4.03 |
| 多轮上下文退化 | 从第几轮开始变差 | 3.55 |

> 评分维度：用户痛点强度 × 发生频率 × 商业价值 × 技术可行性

### 3.2 选定理由

**最痛**：用户转圈 20 分钟，没人能解释。开发者要在日志里手动拼时间线；SRE 告警只说"慢了"，定位不到具体步骤。

**最频**：每天都在发生，非偶发故障，有持续优化空间。

**最可做**：只需时间、调用关系、状态三类数据，无需内容理解，减少合规风险。

**差异最大**：竞品在这个场景缺口最明显——都有时序线，但没有关键路径算法。

### 3.3 三类用户的具体痛点

| 用户角色 | 现在的困境 | 期望的结果 |
|---|---|---|
| 终端用户 | 不知道 Agent 是还在运行还是已卡死 | 进度可见，知道在等什么 |
| 开发者 | 模型/工具/RAG/子 Agent 日志散落，时间线拼不出来 | 一屏看出瓶颈在哪一步 |
| SRE | 告警只说"慢"，定位不到 Span | 告警直接跳转到关键路径 |

### 3.4 成功验收标准

| 指标 | 目标值 |
|---|---:|
| 首次定位中位时长 | ≤ 30 秒 |
| Top-1 瓶颈识别准确率 | ≥ 80% |
| 告警到目标 Span 点击次数 | ≤ 3 次 |
| 诊断"有帮助"反馈率 | ≥ 70% |

## 四、差异化核心：不是画出链路，是解释等待

### 4.1 七个差异点（P0/P1/P2）

**P0 — 必须首期实现，这是核心竞争力：**

| 差异点 | 竞品现状 | 我们的方案 |
|---|---|---|
| **墙钟关键路径** | 展示每个 Span 的 duration | 计算真正影响端到端时间的路径，不把并行分支相加；显示每节点边际贡献 |
| **采集健康度** | 缺失数据不显示 | 断链/时钟偏差/字段缺失作为一等信息显示；不完整时不输出高置信根因 |

**P1 — 体验关键，第二阶段实现：**

| 差异点 | 具体方案 |
|---|---|
| **等待语义化** | 把空白时间分为：模型排队/首 Token 等待/工具网络延迟/重试退避/串行化/本地计算 |
| **自动正常基线** | 自动匹配同版本同意图的成功请求；差异视图只突出关键变化 |
| **证据化 AI 诊断** | 每条结论固定包含：根因候选 + 支持证据 + 反证/未知 + 置信度 + 下一步动作 |

**P2 — 长期差异化：**

- 问题导向入口（首屏选"慢/错/贵/不准"，而非先选视图）
- 用户等待时间线（提交 → 排队 → 首 Token → 完成，与工程 Span 对齐）

### 4.2 一句话说清差异

> **竞品的答案**："这个 Span 花了 14 分钟。"  
> **我们的答案**："正常同类请求 1.8 秒。本次因 3 次 504 重试达到 14 分钟，占关键路径 70%；下一步建议查工具服务端错误日志。"

### 4.3 AI 能力设计原则

- **算法先行**：关键路径、重试检测、等待分类由确定性算法完成；大模型负责解释和排序，不发明时间关系
- **数据不全不下结论**：有断链/偏差/缺失时只给补采集建议
- **证据必须可点击验证**：每个支持证据都能跳转到原始 Span

## 五、技术可行性：两周原型，三个核心难点

### 5.1 两周路线

| 周次 | 里程碑 | 核心工作 |
|---|---|---|
| 第 2 周 | 可演示闭环 | OTel 采集接入；Trace 列表 + 关键路径时间线；采集健康检查；构造三类故障（慢工具/重试/上下文膨胀） |
| 第 3 周 | 差异化验证 | 正常基线自动匹配；等待类型与贡献率；证据化 AI 根因；20-30 条专家标注 Trace 做对比评测 |

### 5.2 三个核心难点（不可回避）

| 难点 | 为什么难 | 处理路径 |
|---|---|---|
| **异步与多 Agent** | 父子关系无法表达因果（消息队列/委派） | 使用 Span Link；区分调度与执行 |
| **流式输出** | duration 表达不了用户感知 | 记录 first token / last token 时间戳事件 |
| **时钟偏差** | 多服务时间线错位、出现负耗时 | Collector 校时 + 偏差估计 + 显性告警 |

### 5.3 Go 门槛（进入下阶段的准入条件）

```
✅ 关键字段覆盖率 ≥ 90%
✅ Top-1 瓶颈准确率 ≥ 80%
✅ 目标用户完成定位时长 ≤ 60 秒
✅ 比基线产品定位时间减少 ≥ 30%
```

## 六、战略判断：半年路线图

### 6.1 六个行业趋势

1. **OTel 语义加速收敛** → 兼容性成为竞争点，我们应基于 OTel 扩展而非造私有协议
2. **Trace 从树变图** → 跨 Trace Link、异步、多 Agent 委派成为一等对象，首期就要保留图算法
3. **观测与评测融合** → 问题 Trace 一键进回归集；首期应留接口
4. **AI Copilot 走向行动** → 不只总结，还要能建查询/数据集/告警
5. **采集双轨** → 语义埋点（高层）+ eBPF（运行时补充）
6. **治理成为购买条件** → 脱敏/保留期/RBAC/成本可预估

### 6.2 半年产品路线

| 月份 | 目标 | 关键交付 |
|---|---|---|
| 第 1 月 | 做透慢请求 | 关键路径 + 等待分类 + 采集健康 |
| 第 2 月 | 证明优于竞品 | 基线与差异视图；内测用户验证 |
| 第 3 月 | 生产可用 | 采样/脱敏/RBAC/告警/成本估算 |
| 第 4 月 | 扩展异常与成本 | 失败根因 + Token 成本归因 |
| 第 5 月 | 连接会话与质量 | Session 视图 + 多轮退化分析 |
| 第 6 月 | AI 闭环 | 问题 Trace 回流评测 + 修复验证 |

> **最佳切入**：不是追齐竞品所有模块，而是把"用户等待 → 关键路径 → 证据根因 → 修复验证"这一条链做到明显更快、更可信。
