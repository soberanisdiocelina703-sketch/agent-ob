# 任务 09｜用户/交互/视觉深挖：阿里云链路追踪体验分析

> 本次选择阿里云 AgentLoop / 云监控 2.0 AI Agent 可观测作为深挖对象。分析基于官方文档的信息结构；视觉细节仍需控制台实机和截图补证。

## 1. 目标用户与核心任务

### 主要用户

- Agent 应用开发者：排查模型、Prompt、工具、RAG、MCP 和框架逻辑。
- SRE/平台工程师：处理告警、性能、错误、容量和底层服务。
- AI 产品/运营：关注用户、会话、Token、成本和模型/工具表现。

### 核心任务

从异常趋势或用户投诉出发，找到目标 Trace，理解内部执行过程，定位具体 Span，并联动日志/事件/微服务继续排查。

## 2. 用户旅程图

| 阶段 | 触发 | 用户问题 | 产品触点 | 情绪/风险 |
|---|---|---|---|---|
| 发现 | 告警、用户投诉、指标突变 | 影响多大？ | 总览、Agent 列表、场景化分析 | 焦虑，需要快速缩小范围 |
| 筛选 | Trace 数量很多 | 哪类请求异常？ | 搜索表达式、聚合、趋势图 | 需要熟悉字段和查询语法 |
| 确认 | 找到候选 Trace | 是不是这次问题？ | Trace 输入输出、耗时、Token、用户/会话 | 摘要有效，确认成本低 |
| 理解 | 链路复杂 | 调用结构和时间如何？ | 五种 Trace 视图 | 视图选择可能造成负担 |
| 定位 | 某节点异常 | 为什么慢/错？ | Span Info、Attributes、Resources、Events、Links | 信息密度高，专家友好 |
| 联动 | 根因可能在底层 | 下一步查什么？ | 日志、事件、微服务跳转 | 跨系统但上下文可延续 |
| 治理 | 问题反复出现 | 如何长期监控？ | Token/模型/工具大盘、告警 | 从个案转向趋势治理 |

## 3. 交互模式库

### 模式一：全局到局部下钻

```text
总览/实体 → Trace 列表 → Trace 详情 → Span 详情 → 日志/资源
```

优点：符合传统 APM 用户的认知。

问题：第一次使用 Agent 观测的产品/算法人员可能不熟悉 Trace/Span 层级。

### 模式二：多视图切换

同一 Trace 提供调用树、链路图、时序线、推理轨迹、链路分析。

优点：每种问题都有适合表达方式。

问题：视图切换会改变空间结构和阅读方式，用户必须知道“哪个视图适合哪个问题”。

改进：根据入口问题自动推荐，并保留同一节点选择状态。

### 模式三：主从详情

时序线左侧是 Span 列表/瀑布，右侧是选中 Span 的详情页签。

优点：列表与证据同屏，适合快速连续浏览。

问题：窄屏或字段很长时容易拥挤；大量 JSON 会压缩时间线空间。

改进：支持详情抽屉宽度、结构化摘要、关键字段置顶和大内容单独打开。

### 模式四：格式化/原始数据切换

输入输出支持 Pretty 与 Raw，推理轨迹区分 System/User/Assistant/Tool。

优点：兼顾业务阅读和工程排查。

问题：敏感内容和超长上下文容易造成信息暴露与性能问题。

改进：默认摘要与脱敏，按权限加载原文；超长内容虚拟化渲染。

### 模式五：轨迹/聚合切换

链路图既能显示原始调用顺序，也可合并相同 Span。

优点：兼顾单次因果与热点模式。

问题：聚合后可能失去具体时序和异常实例，需要清楚标识聚合规则。

## 4. 信息层级分析

### 第一层：结果与影响

Trace 总耗时、Token、状态、输入输出、用户和会话。

### 第二层：结构与时间

Span 类型、父子、拓扑、甘特条、调用次数和错误。

### 第三层：语义与资源

Prompt/Response、Tool 参数/结果、模型、SDK、主机和服务。

### 第四层：诊断证据

日志、事件、Link、错误堆栈和基础设施上下文。

整体层级合理，但“诊断结论”没有独立成为第一层，仍需用户从证据中自行总结。

## 5. 视觉风格拆解

### 官方文档可确认的视觉编码

- Span 使用类型标签区分 ENTRY/AGENT/LLM/TOOL。
- 时间使用甘特/瀑布长条编码。
- 推理轨迹用气泡和角色区分 System/User/Assistant/Tool。
- 链路图用节点、连线和 status/duration/calls 指标表达拓扑。
- 概览和场景分析以指标卡和趋势图为主。

### 视觉优点

- 标签、层级缩进和时间条组合，能同时表达结构和耗时。
- 推理轨迹将技术 Span 翻译为对话语义，降低阅读原始 JSON 的成本。
- 多模态原生预览适合新型 Agent 输出。

### 视觉风险

- 颜色同时承担 Span 类型、状态和消息角色时可能发生编码冲突。
- 超深调用树和宽瀑布图需要横向空间。
- 指标卡、标签、页签和辅助按钮过多可能分散注意力。
- 拓扑图在循环、重复工具和多 Agent 场景中容易变成“意大利面图”。

## 6. 可用性问题与改进

| 问题 | 影响 | 改进建议 |
|---|---|---|
| 先选视图再解决问题 | 新用户选择困难 | 提供“慢/错/贵/不准”问题入口，自动选视图 |
| 关键路径不突出 | 需要人工读瀑布图 | 默认高亮墙钟关键路径与贡献率 |
| 正常样本需手动寻找 | 判断缺少参照 | 自动匹配同版本/同意图正常基线 |
| 证据分散在多个页签 | 频繁切换 | 生成固定诊断摘要：异常、证据、差异、下一步 |
| 采集缺失不显眼 | 容易错误归因 | 显示覆盖率、断链、时钟偏差和字段缺失 |
| 长文本/JSON 过载 | 难以扫读、渲染慢 | 结构化摘要、差异高亮、按需加载原文 |

## 7. 我们的交互原则

1. 默认先展示诊断结论和证据，再展开原始数据。
2. 在墙钟时间与累计工作量间明确区分。
3. 切换视图时保持相同 Trace、Span 和时间焦点。
4. AI 建议永远能回到原始证据。
5. 对敏感内容默认脱敏，详情按权限加载。
6. 大型 Trace 采用虚拟列表、分层加载和聚合摘要。

## 8. 待实机验证清单

- 五种视图的默认入口、切换成本和节点状态保持。
- 大型 Trace 的展开、搜索、渲染性能。
- 多模态内容预览方式。
- 错误、慢节点和关键指标的实际颜色/优先级。
- 从日志/事件返回 Trace 后上下文是否保留。
- 小屏/低分辨率表现。
