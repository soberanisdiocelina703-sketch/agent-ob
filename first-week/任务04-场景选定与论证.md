# 任务 04｜场景选定与论证：长耗时 Agent 请求的瓶颈定位

## 1. 选定场景

> 当一条 Agent 请求异常缓慢时，帮助开发者在 30 秒内知道：慢在哪个步骤、慢的类型是什么、相对正常基线差多少、下一步应该查什么。

## 2. 用户痛点

会议明确提出：Agent 调用链很长，涉及大模型、工具和其他服务，用户可能“转圈圈 20 分钟”，却不知道为什么。

### 终端用户痛点

- 不知道 Agent 是否仍在工作。
- 不知道等待是正常推理还是系统卡死。
- 长时间无反馈会导致刷新、重复提交或直接流失。

### 开发者痛点

- 模型、工具、RAG、MCP、子 Agent 和重试横跨多个组件。
- 普通日志只能看到事件，不能稳定还原父子、并行和时间关系。
- 单看最大 duration 可能把非关键并行分支误判为瓶颈。
- 找到慢节点后，仍需手工寻找正常请求做对照。

### SRE/平台痛点

- Agent 语义与基础设施指标割裂。
- 告警只能说明“慢了”，不能说明是哪类请求、哪个步骤导致。
- 开发、模型平台、工具服务之间容易互相甩锅。

## 3. 竞品差距

### 已经做好的

- 阿里提供时序线、调用树、推理轨迹等多视图。
- 华为支持 Session 下钻 Trace 和 Span 详情。
- Langfuse 支持 Trace、Agent Graph、Observation 筛选和成本/耗时。

### 仍有空间的

1. 竞品主要展示“发生了什么”，用户仍需人工计算墙钟关键路径。
2. 执行、排队、网络等待、首 Token、重试退避、串行化没有形成统一解释。
3. 正常基线通常需要用户自己筛选和比较。
4. 采集缺失、断链、时钟偏差不够显性，AI 容易基于不完整数据过度归因。
5. 用户感知的排队/首 Token/流式完成与工程 Span 没有完全统一。

## 4. 技术可行性

首期所需数据相对明确：

- Trace ID、Span ID、Parent ID、Span Link。
- 开始/结束时间、状态、Span 类型。
- 模型 request/first token/last token 时间。
- Tool 请求、响应、重试和错误。
- Agent、版本、环境、会话等属性。

只要先覆盖时间、关系和状态，就能实现：

- 关键路径计算。
- 并行/串行识别。
- 重试和退避识别。
- 等待类型初步分类。
- 同类正常 Trace 对比。

不需要第一期就解决主观质量评估或复杂因果推断。

## 5. 商业价值

### 价值容易量化

- 定位时间：从数十分钟降到 30–60 秒。
- MTTR：故障恢复时间下降。
- 性能：P95/P99、TTFT、端到端耗时改善。
- 成本：减少重复调用和无效重试。
- 体验：减少长时间无响应和重复提交。

### 能带动后续模块

性能定位自然需要日志、指标、告警、会话和成本，适合作为观测产品的入口场景。问题 Trace 还可以沉淀为后续评测和回归数据集。

## 6. 为什么不先选其他场景

| 场景 | 暂不优先的原因 |
|---|---|
| 异常根因 | 与性能场景共用底座，可作为第二阶段扩展；首期错误类型更分散 |
| Token/成本 | 容易做聚合，但难形成比竞品明显更强的首个体验 |
| 错误输出 | 价值很高，但需要可靠人工标签、Rubric 和多类质量真值 |
| 多轮退化 | 依赖 Session 数据完整度，问题频率与价值需先访谈验证 |

## 7. 产品目标

### 核心任务完成标准

用户在一条慢请求中：

1. 60 秒内找到正确瓶颈节点。
2. 正确判断它属于执行、等待、重试、串行化或采集缺失。
3. 能说出下一步排查动作。

### 指标

- 首次定位中位时长 ≤ 30 秒。
- Top-1 瓶颈识别准确率 ≥ 80%。
- 告警/会话到目标 Span 点击数 ≤ 3。
- 诊断建议“有帮助”反馈率 ≥ 70%。
- 采集覆盖率和断链率可见。

## 8. 风险与应对

- **风险：高耗时并非故障。** 应对：区分策略性长任务与异常偏离基线。
- **风险：Span 不完整。** 应对：先给采集健康度，不输出高置信根因。
- **风险：AI 误导。** 应对：AI 只排序候选，必须展示证据、反证和置信度。
- **风险：敏感数据。** 应对：采集端脱敏、字段权限、保留期和导出审计。

## 9. 结论

该场景同时满足痛点明确、竞品仍有差距、技术底座可复用、价值可量化四个条件，适合作为第一个做透的链路管理场景。
