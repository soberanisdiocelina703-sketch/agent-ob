# 任务 07｜技术选型侦察：竞品技术栈与实现方式推测

## 1. 说明

本文件区分：

- **官方事实**：厂商文档明确描述。
- **合理推测**：基于公开接口、字段、依赖产品和行业实现方式推断，不代表厂商披露。

## 2. 阿里云技术路线

### 官方事实

- Python 使用自动探针/`aliyun-bootstrap`，Go 使用 `instgo`，Dify 使用内置 OTel。
- 支持 OpenTelemetry 标准属性和 GenAI 扩展属性。
- Span 类型覆盖 Agent、LLM、Tool、MCP、Memory、Chain、Retriever、Embedding。
- 支持自定义埋点、日志联动、事件和微服务链路。
- AgentLoop 审计/AI Coding Agent 方向存在 Hook、LoongSuite Pilot 和 eBPF 运行时采集。

### 合理推测

```text
自动探针 / OTel / Hook / eBPF
        ↓
LoongSuite/Collector 接入与批处理
        ↓
ARMS/云监控 Trace 存储与指标聚合
        ↓
Trace 重建、拓扑/时序/推理视图
        ↓
SLS 日志、事件、微服务与智能告警联动
```

- 前端视图大概率由统一 Trace/Span 数据经不同投影生成。
- 聚合视图按 Span 名称、类型和关键属性合并节点。
- 推理轨迹通过标准化 System/User/Assistant/Tool 内容字段重建。
- eBPF 更适合补充进程、网络和文件副作用，不应替代应用内语义埋点。

### 观察

阿里技术优势是已有全栈可观测底座，难点是兼容大量框架版本并维持语义字段一致。

## 3. 华为云技术路线

### 官方事实

- 第三方 Agent 使用 OpenTelemetry Python SDK、OTLP Exporter 和 Traceloop SDK。
- Trace 通过专用 endpoint/token 上报并直接写入 APM。
- `OTEL_SERVICE_NAME` 和 `gen_ai.*` 字段有严格命名与类型规范。
- Trace、Metric、Log 分别进入 APM、AOM、LTS。
- Conversation ID 用于会话串联；Agent ID/资源属性用于统一视图。

### 合理推测

```text
AgentArts 原生埋点 / 第三方 OTel SDK
        ↓
OTLP Trace Endpoint + 鉴权
        ↓
APM(Trace) / AOM(Metric) / LTS(Log)
        ↓
AgentArts 领域聚合层
        ↓
Session、Trace、Span、标注、回流与评测
```

- AgentArts 控制台可能根据 Agent ID、Conversation ID 和 Trace ID 组合三个底层服务的查询结果。
- 严格字段规范保证统一解析与图表，但字段缺失会导致“数据已上报、界面不可用”。
- Trace 回流将观测数据映射为评测数据集要求的 Input/Output/Metadata 结构。

### 观察

华为技术优势是开发/观测/评测统一；短板是跨服务一致性、字段接入复杂度和开发态数据覆盖。

## 4. Langfuse 技术路线

### 官方事实

Langfuse v4 基础组件：

- Web Container。
- Worker Container。
- PostgreSQL。
- ClickHouse。
- Redis/Valkey。
- S3/Blob Storage。

v4 数据模型：

- OTel-based ingestion。
- `events_full`：完整不可变事件。
- `events_core`：面向查询、截断大字段的轻量投影，由物化视图生成。
- Trace 表达为根 Observation，`trace_id` 用于聚合关联。
- 摄取路径包含队列、S3-first 持久化和批量写入 ClickHouse。

### 合理推测

```text
SDK / Framework Instrumentation / OTLP
        ↓
Web Ingestion API
        ↓
S3 原始事件 + Redis/Queue
        ↓
Worker 批处理
        ↓
ClickHouse events_full / events_core
        ↓
Observations UI / Graph / Metrics / API / Eval
```

- PostgreSQL 主要存用户、项目、Prompt、数据集、配置等事务数据。
- ClickHouse 承担大规模 Trace 事件检索和聚合。
- S3 保存大对象、多模态和原始事件，降低分析库压力。
- Agent Graph 根据 Observation 的父子、时间和类型推导结构。

### 观察

Langfuse 技术设计适合大规模分析和开放自托管，但生产部署、升级、ClickHouse 容量和对象存储治理需要专业能力。

## 5. 前端/性能对比推测

| 竞品 | 前端信息架构 | 性能策略推测 | 主要挑战 |
|---|---|---|---|
| 阿里 | 多视图、实体页、全局拓扑、场景大盘 | 服务端聚合、分层查询、与 ARMS/SLS 复用 | 超大 Trace 的视图复杂度和查询联动 |
| 华为 | Session/Agent/Trace 领域聚合 | 分别查询 APM/AOM/LTS，再在 AgentArts 组合 | 跨服务延迟和字段一致性 |
| Langfuse | Observation-first 表格、Trace/Graph、评测工作流 | ClickHouse 列式查询、events_core 轻量投影、对象存储大字段 | 自托管资源与深 Trace 数据量 |

## 6. 我们的技术选型建议

### 复用

- OpenTelemetry SDK/Collector。
- GenAI 语义属性。
- 已有日志、指标和告警系统。
- 对象存储保存大输入输出和多模态数据。

### 自建差异能力

- 墙钟关键路径算法。
- 执行/排队/首 Token/网络/重试/串行化分类。
- 正常基线匹配与差异解释。
- 采集健康度、断链与时钟偏差检测。
- 证据化 AI 根因候选。

### 数据架构建议

- Span/Observation 作为事实原子。
- Trace、Session、问题簇作为可重建视图。
- 元数据进入事务库；Span/事件进入列式库；大内容进入对象存储。
- 热查询使用精简投影，详情按需加载完整输入输出。
