# Agent 链路追踪产品研究报告

> **AIinfra 专项 · Agent 观测方向研究**  
> 研究周期：2026-08-07 至 2026-08-10  
> 研究人：王宇航

---

## 执行摘要

本研究针对 Agent 应用链路追踪产品方向，完成了竞品分析、场景选型、差异化定位与技术可行性评估。

**核心结论**：首个产品场景应聚焦**长耗时 Agent 请求的性能瓶颈定位**。当前竞品（阿里云 AgentLoop、华为云 AgentArts、Langfuse）均能展示 Trace 结构，但无法直接回答"用户为什么等了这么久"。我们的机会在于：**30 秒内用证据说清时间花在哪、为什么慢、下一步该查什么**。

核心差异化能力：
- **墙钟关键路径自动计算**：区分并行与串行，计算真正影响端到端时间的路径
- **采集健康度显性化**：断链、时钟偏差、字段缺失作为一等信息，决定诊断可信度
- **等待语义化**：将空白时间分类为模型排队、首 Token、重试退避、串行化等类型
- **自动正常基线匹配**：为异常请求自动调出同类成功请求作对比
- **证据化 AI 诊断**：每条根因候选必须包含支持证据、反证、置信度与下一步动作

## 一、竞品格局分析

### 1.1 竞品选择

研究对象覆盖国内主流云厂商与国际开源标杆：

| 竞品 | 产品形态 | 选择理由 |
|---|---|---|
| **阿里云 AgentLoop** | 公有云商业产品 | 国内云厂商中链路视图与云底座联动最完整，2026-07 刚完成产品升级 |
| **华为云 AgentArts** | 公有云商业产品 | 代表"观测→评测"闭环路线，Trace 数据回流评测集 |
| **Langfuse** | 开源 + SaaS | MIT 开源、跨框架、OTel 原生，适合作为能力对标基线 |

### 1.2 三种竞争路线

```
阿里云 AgentLoop
├─ 定位：云上全栈运维路线
├─ 特点：五种 Trace 视图（调用树/链路图/时序线/推理轨迹/链路分析）
├─ 优势：Agent 语义 + 告警 + 底层资源联动
└─ 不足：视图多，新用户需排障经验才能高效使用

华为云 AgentArts
├─ 定位：观测到评测闭环路线
├─ 特点：Session → Trace 下钻，问题样本一键回流评测
├─ 优势：生产 Trace 直接沉淀为评测资产
└─ 不足：Trace/Metric/Log 分属 APM/AOM/LTS 三个产品

Langfuse
├─ 定位：开放数据平台路线
├─ 特点：MIT 开源、跨模型跨框架、Observation-first 数据模型
├─ 优势：OTel 原生、可私有化、AI Engineering 全链路
└─ 不足：自托管包含 PG+ClickHouse+Redis+对象存储，运维成本高
```

### 1.3 共同特征与盲点

**三家的共同基础**（我们应继承）：
- Session → Trace → Span 三层结构
- OpenTelemetry + GenAI 语义属性兼容
- 列表总览 → 筛选 → 下钻的排障入口
- AI 能力从"总结"向"行动"演化

**三家的共同盲点**（我们的切入点）：
1. **展示耗时但不计算关键路径**：用户需手动从瀑布图中判断哪些 Span 真正影响端到端时间
2. **采集问题被当业务问题处理**：断链、时钟偏差导致的错误结论不会被标识
3. **AI 根因缺乏可验证证据**：诊断结论无法追溯到支撑证据，用户难以信任
4. **正常基线需人工查找**：无法自动调出同类成功请求作对比

## 二、场景选型与论证

### 2.1 候选场景评估

按痛点强度、发生频率、商业价值、技术可行性四维加权评分：

| 场景 | 用户在问什么 | 加权分 |
|---|---|---:|
| **长耗时瓶颈定位** | 时间到底花在哪一步 | **4.75** ⭐ |
| 失败根因定位 | 为什么中断、谁的责任 | 4.45 |
| 错误输出复盘 | 是检索、Prompt 还是工具 | 4.25 |
| Token 成本治理 | 钱花在哪个 Agent | 4.03 |
| 多轮上下文退化 | 从第几轮开始变差 | 3.55 |

### 2.2 首选场景：长耗时请求的性能瓶颈定位

**选型理由**：

**① 痛点最强**  
用户转圈 20 分钟，没人能解释为什么。开发者需在多处日志中手动拼时间线；SRE 告警只说"慢了"，定位不到具体步骤；终端用户不知道 Agent 是还在工作还是已卡死。

**② 发生频率最高**  
每天都在发生，非偶发故障，有持续优化价值。

**③ 技术可行性最高**  
只需时间、调用关系、状态三类数据，无需内容理解，合规风险最低。

**④ 竞品差距最大**  
三家均有时序线视图，但都没有关键路径自动计算——这是最大的空白地带。

### 2.3 三类用户的具体需求

| 用户角色 | 现状困境 | 期望结果 |
|---|---|---|
| **👤 终端用户** | 不知道 Agent 还在运行还是已卡死 | 进度可见，知道在等什么 |
| **👨‍💻 开发者** | 模型/工具/RAG/子 Agent 日志散落，时间线拼不出来 | 一屏看出瓶颈在哪一步 |
| **🔧 SRE** | 告警只说"慢"，定位不到 Span | 告警直接跳转到关键路径 |

### 2.4 成功标准

| 指标 | 目标值 | 对标基准 |
|---|---:|---|
| 首次定位中位时长 | ≤ 30 秒 | 竞品普遍 30 分钟+ |
| Top-1 瓶颈识别准确率 | ≥ 80% | 专家人工判断水平 |
| 告警到目标 Span 点击次数 | ≤ 3 次 | 竞品 10+ 次 |
| 诊断"有帮助"反馈率 | ≥ 70% | 主观满意度门槛 |

## 三、产品差异化策略

### 3.1 核心定位

> **竞品**：让用户"看见一条 Trace"  
> **我们**：让用户"在 30 秒内用证据知道时间花在哪、为什么慢、下一步查什么"

### 3.2 差异化能力矩阵

#### P0 级（首期必须实现，核心竞争力）

| 能力 | 竞品现状 | 我们的方案 | 价值 |
|---|---|---|---|
| **墙钟关键路径** | 展示每个 Span 的 duration | 计算真正影响端到端时间的路径，不简单叠加并行分支；显示每节点边际贡献 | 减少超大 Trace 的人工阅读和误判 |
| **采集健康度** | 缺失数据不显示或被当正常数据 | 断链、时钟偏差、字段缺失作为一等信息显示；数据不完整时不输出高置信根因 | 诊断结论的可信度有据可查 |

#### P1 级（体验关键，第二阶段实现）

| 能力 | 方案 | 价值 |
|---|---|---|
| **等待语义化** | 将空白时间分为：模型排队/首 Token/工具网络/重试退避/串行化/本地计算/采集缺失 | 同样 10 秒，不同等待类型对应不同优化动作 |
| **自动正常基线** | 自动匹配同版本同意图的成功请求；差异视图只突出关键变化 | 把"这个 Span 14 分钟"升级为"正常同类 1.8 秒，本次因 3 次 504 重试" |
| **证据化 AI 诊断** | 每条结论固定包含：根因候选 + 支持证据 + 反证/未知 + 置信度 + 下一步动作 | AI 建议可验证、可追溯 |

#### P2 级（长期差异化）

- **问题导向入口**：首屏选"慢/错/贵/不准"，而非先选视图
- **用户等待时间线**：提交 → 排队 → 首 Token → 完成，与工程 Span 对齐

### 3.3 对比示例

**场景**：用户报告某 Agent 请求耗时 14 分钟

**竞品诊断**：
> "Tool_call_xyz Span 耗时 840 秒。"

**我们的诊断**：
> "正常同类请求（相同 Agent、版本、工具集）平均 1.8 秒，P95 为 3.2 秒。  
> 本次因下游工具服务返回 3 次 504 超时触发指数退避，累计等待 820 秒，占关键路径 97.6%。  
> **证据**：Span abc123、def456、ghi789 连续 504；重试间隔 2s/4s/8s 符合指数退避。  
> **反证**：缺少工具服务端 CPU/内存指标，无法确认是容量问题还是代码 bug。  
> **置信度**：85%  
> **下一步**：建议查工具服务 `service-x` 在 2026-08-10 14:32–14:46 的错误日志。"

## 四、技术架构与实现路径

### 4.1 技术选型原则

**直接复用**（站在巨人肩膀上）：
- OpenTelemetry SDK 与 Collector
- GenAI 语义属性（`gen_ai.*`）
- 已有日志/指标/告警基础设施
- 对象存储放大内容（Prompt/Output）

**自主研发**（核心差异化）：
- 墙钟关键路径算法（图算法 + 并行感知）
- 等待类型分类器（规则 + 语义）
- 正常基线自动匹配引擎
- 采集健康度检测
- 证据化 AI 根因引擎

### 4.2 核心算法设计

#### 关键路径计算

1. 按 parent_span_id 和 Span Link 构建有向图
2. 校验时间区间、检测环、估计时钟偏差
3. 合并同步调用和异步等待关系
4. 计算从根到叶的最长墙钟路径（非 duration 简单求和）
5. 计算每节点对端到端时间的边际贡献

#### 等待分类（规则优先）

- LLM request → first token：模型排队/首包等待
- Tool client → server：网络与服务端执行
- 同操作重复 + 错误：重试
- 重试间隔递增：退避
- 同层步骤无重叠且无依赖：潜在串行化
- 父 Span 活跃但无子事件：本地计算/等待/采集缺失候选

#### 正常基线匹配

```
匹配条件（优先级递减）：
1. 同 Agent + 同 Trace 名/意图
2. 同版本 + 同环境
3. 相似工具集合 + 相似输入 Token
4. 状态成功 + 耗时位于正常分位（P50–P95）

必须展示匹配依据，避免"黑盒基线"
```

### 4.3 三个核心技术难点

| 难点 | 为什么难 | 处理路径 |
|---|---|---|
| **异步与多 Agent** | 父子关系无法表达因果（消息队列、跨服务委派） | 使用 Span Link；区分调度时间与执行时间 |
| **流式输出** | duration 无法表达用户感知（首 Token 到末 Token 差异大） | 记录 first_token / last_token 时间戳事件 |
| **时钟偏差** | 多服务时间线错位，甚至出现负耗时 | Collector 校时 + 偏差估计 + 显性告警 |

### 4.4 AI 能力设计原则

**算法先行，AI 负责解释**  
关键路径、重试检测、等待分类由确定性算法完成；大模型负责排序、解释、生成下一步建议，但不发明时间因果关系。

**数据不全不下结论**  
有断链、时钟偏差、字段缺失时，只给出采集健康度报告和补采集建议，不输出根因候选。

**证据必须可点击验证**  
每个支持证据都能跳转到原始 Span、日志或指标，用户可独立验证。

## 五、产品形态设计

### 5.1 页面结构演进

**竞品常见方式**：
```
Trace 列表 → 选择一条 → 选择视图（树/图/时序线/轨迹/分析）→ 手动判断
```

**我们的方式**：
```
问题入口（慢/错/贵/不准）→ 自动编排视图 → 关键路径高亮 + 基线对比 → 证据化根因候选
```

### 5.2 核心页面元素

**① 采集健康度面板**（首屏顶部）
- 字段覆盖率：90% ✅
- 时钟偏差：±50ms ⚠️
- 断链检测：3 处 ❌
- 可信度：中等（部分根因候选置信度降低）

**② 关键路径时间线**
- 自动高亮影响端到端时间的 Span
- 显示每节点边际贡献（绝对时间 + 占比）
- 区分串行、并行、等待类型

**③ 基线对比卡片**
- 正常同类请求：P50 1.8s / P95 3.2s / 样本数 248
- 本次请求：840s（+46,567%）
- 关键差异：工具调用次数 1 → 4，其中 3 次重试

**④ 根因候选列表**
- 每条包含：根因描述 / 支持证据（可点击）/ 反证或未知 / 置信度 / 下一步
- 按置信度排序
- 支持"有帮助"/"无帮助"反馈

## 六、商业模式与定价策略

### 6.1 竞品定价分析

| 竞品 | 计费方式 | 客户痛点 |
|---|---|---|
| **阿里云** | ARMS/SLS 用量 + AI 积分增值 | 跨三个产品出账，算不清总成本 |
| **华为云** | 界面免费，APM/AOM/LTS 收数据费 | 三类数据分别计费 |
| **Langfuse** | OSS 免费，Cloud 按 units 计费（$29–$2499+/月） | 深链路 units 增长快于请求数 |

### 6.2 定价建议

**计费单位**：
- 有效 Span 数据量（按存储 + 保留期）
- AI 诊断按执行量单独计费
- 丢弃数据（采样外、过期）不计费

**必须提供**：
- 接入前成本估算器
- 每项目预算与费用告警
- AI 分析费用上限
- 统一账单（不跨产品出账）

## 七、行业趋势与战略判断

### 7.1 六个关键趋势

**① OpenTelemetry 语义加速收敛**  
字段标准化速度加快，兼容性成为竞争点。产品应基于 OTel 扩展而非造私有协议。

**② Trace 从树扩展为图**  
跨 Trace Link、异步任务、Agent 委派成为一等对象。图算法需从首期就设计进数据模型。

**③ 观测与评测融合**  
问题 Trace 一键进入回归集，性能/质量/成本三维度在同一版本对比。即使首期聚焦性能，也应为评测留接口。

**④ AI Copilot 走向行动**  
不只总结，还能建查询、数据集、告警规则。AI 能力需从"解释"向"执行"演进。

**⑤ 采集双轨并行**  
语义埋点（Agent/LLM/Tool 高层语义）+ eBPF（运行时细节补充），两条路径将长期共存。

**⑥ 治理成为购买条件**  
脱敏、保留期、RBAC、成本可预估。中大型企业不购买治理能力不到位的产品。

### 7.2 产品定位建议

**不是追齐竞品所有模块**，而是把"用户等待 → 关键路径 → 证据根因 → 修复验证"这一条链做到**明显更快、更可信**。

第一个月做透慢请求，证明核心价值后再横向扩展到失败根因、成本归因、质量评测。

## 八、风险与应对

| 风险类别 | 具体风险 | 应对策略 |
|---|---|---|
| **产品风险** | 长耗时未必是故障（策略性长任务） | 区分策略性长任务与偏离基线；提供"标记为正常"功能 |
| **技术风险** | Span 数据不完整导致误诊 | 采集健康度显性化；数据不完整时不输出高置信根因 |
| **AI 风险** | 根因候选错误损害可信度 | 只排序候选而非给绝对结论；必须展示证据与置信度；支持用户反馈 |
| **合规风险** | Prompt/Output 包含敏感数据 | 采集端脱敏；字段级 RBAC；审计日志；保留期自动清理 |
| **商业风险** | 计费复杂度影响采购决策 | 提供接入前成本估算器；统一账单；预算告警 |

## 九、结论

Agent 链路追踪市场已有三家主流竞品覆盖，但在"用户为什么等待"这一核心问题上均留有空白。

我们的机会在于：**不只展示链路结构，而是直接回答关键问题，并用可验证的证据支撑每个结论**。

首个场景应选择**长耗时请求的性能瓶颈定位**，通过关键路径自动计算、采集健康度显性化、自动基线对比、证据化 AI 诊断四项核心能力，将定位时间从竞品的 30 分钟缩短到 30 秒，Top-1 瓶颈准确率达到 80% 以上。

这不是技术演示，而是直接可交付的产品方向——用户在生产环境遇到慢请求时，我们的产品应该能立即告诉他：慢在哪、为什么、下一步查什么。
