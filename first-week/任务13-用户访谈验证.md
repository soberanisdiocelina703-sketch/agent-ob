# 任务 13｜用户访谈验证：3 位目标用户的验证方案

> 当前状态：已完成招募标准、访谈提纲、任务脚本和记录表；**尚未完成真实访谈，因此不填写虚构结论**。

## 1. 需要验证的核心假设

1. 长耗时 Agent 请求是高频、高成本问题。
2. 用户目前无法快速找到墙钟关键路径。
3. 自动正常基线比增加更多 Trace 图表更有价值。
4. AI 根因只有绑定证据时才可信。
5. OTel/探针接入和必要数据采集在目标环境中可接受。

## 2. 三类目标用户

| 编号 | 角色 | 筛选条件 | 重点验证 |
|---|---|---|---|
| U1 | Agent 应用开发者 | 近 3 个月开发过 LLM + Tool/RAG；亲自排查过慢请求 | 当前排障路径、关键路径、Span 粒度 |
| U2 | 平台/SRE | 维护线上 AI/微服务；使用过 APM、日志或告警 | 告警到根因、基础设施联动、可信度 |
| U3 | AI 产品/运营 | 对等待、成功率、成本或版本效果负责 | 用户影响、业务指标、报告与决策 |

## 3. 30 分钟访谈结构

### A. 背景与筛选（5 分钟）

1. 你负责的 Agent 做什么？主要框架、模型和工具是什么？
2. 线上大概有多少请求/用户？是否有流式输出和多 Agent？
3. 最近一次用户等待很久是什么时候？

### B. 真实事件回放（10 分钟）

1. 问题最初由什么信号发现？
2. 请按时间顺序讲你做的每一步。
3. 先看哪个工具/页面？为什么？
4. 在哪些系统间切换？复制了哪些 ID？
5. 最终根因是什么？定位花了多久、多少人？
6. 有无误判、数据缺失或互相甩锅？

### C. 原型任务（10 分钟）

给用户一条包含“慢工具 + 三次重试 + 长模型调用”的 Trace 原型，让其：

1. 找到主要瓶颈。
2. 判断属于执行、等待、重试、串行化还是采集缺失。
3. 说出下一步行动。
4. 判断 AI 结论是否可信，还缺什么证据。

记录：完成时间、点击数、停顿、错误判断、主动关注字段和原话。

### D. 功能与商业取舍（5 分钟）

1. 调用树、拓扑、时序线、推理轨迹只能留两个，你选什么？
2. 自动根因、正常基线、日志联动、会话回放请排序。
3. 哪些 Prompt/Output/Tool 参数不能保存？谁能看？保留多久？
4. 什么接入成本或计费方式会阻止采用？

## 4. 避免诱导

- 先问真实事件，再展示概念。
- 不问“这个功能好吗”，问“下次会在哪一步用它、替代什么工具”。
- 对“会用”继续追问具体频率、节省时间和谁有采购/接入权。
- 区分开发调试、灰度、生产和事后复盘。
- 不把“慢请求很多”提示给受访者，让其先自行描述痛点。

## 7. 验证门槛

### Go

- 至少 2/3 近三个月遇到长耗时且定位超过 30 分钟。
- 至少 2/3 用原型在 60 秒内找到正确瓶颈。
- 至少 2/3 将关键路径或正常基线排在前两位。
- 没有不可化解的数据合规或接入阻力。

### Pivot

- 性能问题低频、输出质量高频：转向“错误答案轨迹复盘 + 评测回流”。
- 开发者能定位但 SRE 无法联动：转向 Trace/APM/Log 关联。
- 用户不信 AI：AI 降级为证据摘要与查询助手。
- 接入字段经常缺失：先做采集健康和字段修复产品。

### No-Go

- 3/3 现有工具都能在 5 分钟内稳定定位。
- 关键诊断数据普遍不可采集，脱敏后也失去价值。
- 目标框架无法稳定得到父子、Tool、LLM 和 first token 数据。
