# Agent 可观测与链路追踪 —— 会议重点整理

> 本文用于后续 PPT / 汇报材料撰写。
>
> 会议主线：**为什么要做 Agent 可观测 → 为什么重点做链路追踪 → 当前业务怎么用 → 现阶段痛点是什么 → 未来往根因分析和故障协同演进。**

---

## 一、可观测的基本定位

可观测的目标，是通过采集应用运行过程中的各种信息，理解系统当前的运行状态，并在出现问题时帮助定位原因。

传统可观测主要包含几个维度：

| 维度 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| **Metrics（指标）** | 发生了什么现象 | CPU 使用率、错误率、请求量、Token 消耗 |
| **Logs（日志）** | 为什么出现这个现象 | 程序运行与报错的具体信息 |
| **Trace（链路）** | 问题发生在哪一段调用过程中 | 一次请求经过的多个服务、组件和步骤 |
| **Events（事件）** | 系统发生了什么变化 | 版本发布、配置变更、数据库变更 |

**关键结论：链路追踪只是整个可观测体系中的一个组成部分，并不等于全部可观测。**

---

## 二、为什么 Agent 仍然需要传统可观测体系

Agent 本质上依然是一个运行中的软件系统，因此传统的 Metrics、Logs、Trace 等能力仍然需要。

**不同点在于：**

- 传统软件的调用路径更多是由代码预先确定；
- 而 Agent 的部分执行路径可能由**大模型在运行过程中动态决定**。

例如 Agent 可能动态地：

```
调用大模型 → 调 Tool → 查 RAG → 调浏览器 → 调另一个 Agent → 再调用模型
```

因此 Agent 的上下游依赖会更多、更动态，链路也会更加复杂。

**所以 Agent 可观测并不是抛弃传统可观测，而是：**

> 建立在传统可观测体系基础之上，针对 Agent、LLM、Tool、RAG、Multi-Agent 等新的调用形式进行扩展。

---

## 三、为什么当前重点做 Trace 链路追踪

**Metrics 更多负责发现问题。** 例如：错误率突然升高。

但仅仅看到错误率升高，并不知道问题具体发生在哪里。

**Logs 可以帮助进一步排查原因**，但在分布式系统和 Agent 场景下，一次请求可能跨越很多系统，仅靠日志很难快速知道应该去查哪个系统。

**因此需要 Trace。** Trace 会把整个调用过程按照调用关系组织成一棵调用树：

```
用户输入
  └─ Agent
       ├─ Tool
       ├─ RAG
       ├─ LLM
       └─ 其他 Agent
            └─ 最终输出
```

这样出了问题之后，可以快速回答：

> **"到底是哪一步出了问题？"**

因此链路追踪对于**智能体开发人员**和**智能体运维人员**来说，是排障过程中非常重要的基础能力。

---

## 四、为什么"现在"做 Agent 链路追踪

目前 KC 等 Agent 业务已经从早期探索阶段逐渐进入实际业务使用的深水区。

| 阶段 | 关注点 |
| --- | --- |
| 早期 | Agent 功能能不能做出来 |
| 现在 | Agent 上线以后运行得怎么样？出问题以后怎么发现？问题到底发生在哪？怎么快速排查？ |

因此产生了 Agent 可观测和链路追踪的需求。本质上是：

> 业务从"**建设 Agent**"进入了"**运行和治理 Agent**"的阶段。

---

## 五、当前主要业务方

目前主要业务来源是 **KC**，大体可以拆成两类。

### 第一类：KC 平台自身的 Agent 能力

- 我的分身
- 艺人团队 / 协作类能力
- 平台内部核心 Agent
- Lead Agent 等内部 Agent

这些 Agent 本身需要运行监控和链路排障。

### 第二类：KC 市场中的数字员工 / 业务 Agent

- 教育业务 Agent
- 汽车业务 Agent
- 各业务团队上传的数字员工

这些业务 Agent 在真实使用过程中同样会出现异常，因此也需要接入可观测和链路追踪。

**业务对象可以理解成：KC 平台 Agent + KC 市场中的各种业务 Agent。**

---

## 六、当前技术平台现状

目前底层主要基于 **Langfuse 类 Agent 可观测平台**承接能力，其能力不只包括链路追踪，还包含：

- Trace
- Session / 会话
- User
- Dashboard
- Token 等指标统计
- Agent 运行过程观察
- Evaluation / 评估

### 特别区分：Observability ≠ Evaluation

| | 解决的问题 |
| --- | --- |
| **Observability（可观测）** | Agent 运行过程中发生了什么？ |
| **Evaluation（评估）** | Agent 最终回答得好不好？ |

举例：**调用全部成功，但最终回答内容是错误的。**

- 从 Trace 角度看，链路可能完全正常；
- 从 Evaluation 角度看，回答质量可能只有 1 分。

**所以不能把所有"回答错误"都归结成链路错误。**

---

## 七、当前 Metrics / Logs / Trace 的建设情况

### Metrics

目前已经能通过 Dashboard 展示部分指标：

- Trace 数量
- Case 数量
- Token 消耗
- 调用统计等

Metrics 一般主要用于：**Dashboard 展示 + 监控 + 告警**。

### Logs

目前日志能力还不是完整状态。

- 现在更多是采集与 Trace 相关的一部分上下文和运行信息；
- 但整条调用链对应的**系统级日志还没有完全关联起来**。

未来如果希望做到完整问题分析，就需要把 **Trace + 全链路 Logs** 进一步关联。

### Trace

目前是 Agent 可观测建设中比较重要、也是实际排障使用较多的一部分。

---

## 八、目前用户反馈最多的两类问题

### 1. "大模型又挂了"

这是比较典型的**工程异常**。用户看到：API Error / 模型没有返回 / Agent 没有响应。

运维人员会进入 Trace 排查：

```
用户请求进来了没有？
   ↓
Agent 是否正常执行？
   ↓
Tool 是否正常？
   ↓
LLM 请求有没有发出去？
   ↓
LLM 有没有返回？
   ↓
返回以后应用有没有正确处理？
```

判断示例：

- LLM 本身没返回 → 可能模型服务 / 网络问题；
- LLM 已经返回，但应用没有输出 → 可能 Agent 程序本身的问题。

这是典型的 Trace 排障场景。

### 2. Agent 能运行，但回答很奇怪

例如：用户问中文，却回答了一段日文；或者回答和问题完全不相关。

这种情况下**程序可能没有报错**。需要查看 Trace 中每一步：**哪一步开始产生异常内容？**

- RAG 返回就已经有问题；
- 或者某个 Agent 输出开始出现日文；
- 或者 LLM Prompt 拼接出现异常。

这同样可以借助 Trace 缩小问题范围。但最终判断"回答是否正确"，仍然可能需要结合 **Evaluation**。

---

## 九、延伸场景：数据漂移 / 向量漂移

**场景描述：**

> 整条 Agent 链路调用全部成功，但由于向量模型升级、向量库版本不一致或数据漂移，RAG 检索到了错误内容，最终导致 Agent 给出错误回答。

这个场景本身是成立的，但**已经不完全属于单纯的"链路追踪"能力**。

因为 Trace 最多只能告诉你：

```
RAG 调用了 → 返回成功 → LLM 调用了 → 返回成功
```

但"**为什么 RAG 返回的内容是错的**"，可能还要结合：

- 向量数据库日志
- 模型版本
- Embedding 版本
- 数据更新时间
- Binlog
- 配置变更
- 发布事件
- 其他可观测数据

进行综合判断。

**所以这个能力更准确地应该定义为：根因分析 RCA（Root Cause Analysis），而不是单纯的 Trace。**

---

## 十、创新点如何理解

原始想法是：

> 系统最终表现出错误时，不仅指出"哪一步结果异常"，还进一步找到真正导致异常的上游原因。

例如：

```
最终回答错误
   ↓
Trace 显示：RAG → LLM → Agent 都调用成功
   ↓
进一步关联：Embedding 模型发生版本更新
   ↓
向量库数据未同步重新生成
   ↓
检索排序发生漂移
   ↓
最终导致错误答案
```

这里真正的价值已经从「**链路展示**」升级成了「**智能根因分析**」。

**会议反馈：有价值，且属于运维场景中的重要刚需，但实现难度也明显更高。**

---

## 十一、根因分析为什么比链路追踪更难

因为 **Trace 只是 RCA 的一个输入**。

真正做根因分析，需要综合：

- Trace
- Metrics
- Logs
- Events
- 配置变更
- 数据变化
- 上下游依赖信息

然后再利用大模型进行综合分析。所以它更像：

```
可观测数据 → 上下文聚合 → AI 分析 → 根因推断 → 证据展示
```

甚至可以同时输出：

- 可能根因
- 支持证据
- 反证
- 置信度
- 建议处理方式

这就已经进入 **AIOps / 智能运维** 的范畴了。

---

## 十二、当前最大的两个难点

### 难点一：Agent 上下游链路是否能完整采集

Agent 的调用比传统应用更加复杂，可能包括：

- Agent → Agent
- Agent → LLM
- Agent → Tool
- Agent → Browser
- Agent → RAG
- Agent → 系统
- Agent → 外部服务

**核心挑战：能不能把所有上下游调用完整串成一条 Trace。** 这是偏技术建设层面的基础问题。

### 难点二：有了数据之后，怎么真正帮助用户解决问题

即使已经有 Metrics + Logs + Trace + Events，用户还是需要自己分析。

而最终产品价值应该进一步走向：

```
自动聚合这些信息 → 自动分析异常 → 推断根因 → 给出处理建议
```

**因此"看到问题"还不是终点。**

---

## 十三、未来演进方向

| 阶段 | 目标 | 建设内容 | 回答的问题 |
| --- | --- | --- | --- |
| **第一阶段** | 看见问题 | Metrics + Logs + Trace + Events | 发生了什么？ |
| **第二阶段** | 定位问题 | 把 Agent 整个调用过程串起来 | 问题出现在哪？ |
| **第三阶段** | 分析根因 | 利用大模型综合 Trace + Logs + Metrics + Events | 为什么会出现这个问题？（RCA） |
| **第四阶段** | 故障协同 / 自动处理 | 给出修复建议，甚至自动调用另一个 Agent 执行修复 | 怎么解决？ |

最终形成完整闭环：

```
发现 → 定位 → 分析 → 处理
```

---

## 最值得记住的 5 句话

后续跟导师、PM 或汇报时，建议记住下面五句话：

1. **Agent 可观测不是一套完全新的体系，而是在传统 Metrics、Logs、Trace、Events 基础上的扩展。**
2. **Agent 相比传统应用最大的特点，是调用链更动态、上下游依赖更加丰富，因此 Trace 的完整性更加重要。**
3. **链路追踪解决的是"请求经过哪里、哪一步出现异常"，并不天然解决"最终答案是否正确"。**
4. **当 Trace、Metrics、Logs、Events 被关联起来之后，产品价值可以进一步从"问题定位"升级到"根因分析"。**
5. **Agent 可观测最终可能从"看见问题"演进到"分析问题"，再到"自动解决问题"，形成智能运维闭环。**

---

## 一页 PPT 的主线

```
Agent 上线使用
   → 需要知道运行得怎么样
   → 建设可观测
   → Metrics 发现异常
   → Trace 定位异常步骤
   → Logs / Events 补充上下文
   → AI 根因分析
   → 故障协同 / 自动修复
```

这条主线基本就是这次会议最核心的东西。
